Part 1: the same foundation, a new binding target

Lesson 19 established that Rust's own ABI and layout are not a stable foreign contract — every foreign binding, C, Kotlin, or Swift, has to cross through a deliberately narrow, stable surface. UniFFI's Swift support is built on exactly that discipline: it generates Swift bindings on top of a C-compatible scaffolding layer, the same category of foundation as the raw extern "C" boundary from Lesson 19, not a separate ABI story. Pulsewatch does not need a second UniFFI object for iOS — the exact MobileScorer object and MobileScoringError type exported for Kotlin in Lesson 21 is the same #[uniffi::export] surface Part 4's uniffi-bindgen generate --language swift step reads to emit Swift bindings.

File: path/to/pulsewatch/crates/pulsewatch-scoring/src/mobile.rs — excerpt only, reminding you what already exists there; the bodies below are elided with a comment, they are not re-typed here:

// crates/pulsewatch-scoring/src/mobile.rs (excerpt, already present from Lesson 21 -- not re-created)
// One `impl MobileScorer` block, two generated languages.
#[uniffi::export]
impl MobileScorer {
    #[uniffi::constructor]
    pub fn new(baseline_window_secs: f64, sensitivity: f32) -> Result<Self, MobileScoringError> { /* Lesson 21, Part 4 */ }

    pub fn score(&self, shard_label: String, value: f64, timestamp_unix_ms: i64)
        -> Result<f32, MobileScoringError> { /* Lesson 21, Part 4 */ }
}
// Generated Swift usage looks like ordinary Swift
let scorer = try MobileScorer(baselineWindowSecs: 300.0, sensitivity: 0.62)

do {
    let score = try scorer.score(shardLabel: "shard-42", value: 0.87, timestampUnixMs: 1_726_600_000_000)
} catch MobileScoringError.nonFiniteValue {
    // handle
}

Unlike the Kotlin binding in Lesson 21, there is no scorer.close() to call here, and none should be invented: UniFFI's Swift object support represents MobileScorer as a concrete Swift class holding a reference to the underlying Rust object, so its lifetime follows ordinary Swift ARC. The class's deinit — run automatically once the last Swift reference to scorer goes out of scope — is what releases that reference, with no explicit dispose call for app code to remember. Kotlin needs an explicit close() specifically because the JVM has no reliable, timely finalizer; Swift's deterministic reference counting does not share that problem.

Part 2: async, callbacks, and error mapping

UniFFI documents direct support for exporting async fn Rust functions, generating a Swift async function on the other side, so an iOS app can await a Pulsewatch scoring call without hand-rolled callback plumbing. A Rust Result::Err maps to a thrown Swift error, matching the catch pattern shown above — the same declared-error mapping approach as the cxx bridge in Lesson 20, applied through UniFFI's own scaffolding instead. An async batch method belongs on the very same MobileScorer object, calling back into its own synchronous score method per sample rather than a separate free function. File: path/to/pulsewatch/crates/pulsewatch-scoring/src/mobile.rs (append):

// crates/pulsewatch-scoring/src/mobile.rs -- append to the existing `impl MobileScorer` block from
// Lesson 21, or add this as a second #[uniffi::export] impl block for the
// same type; same struct, same MobileScoringError, no new type.
#[uniffi::export]
impl MobileScorer {
    pub async fn score_batch_async(
        &self,
        shard_label: String,
        values: Vec<f64>,
        timestamps_unix_ms: Vec<i64>,
    ) -> Result<Vec<f32>, MobileScoringError> {
        let mut scores = Vec::with_capacity(values.len());
        for (value, timestamp_unix_ms) in values.into_iter().zip(timestamps_unix_ms) {
            scores.push(self.score(shard_label.clone(), value, timestamp_unix_ms)?);
        }
        Ok(scores)
    }
}

An empty values batch is not an error here: the loop simply does not run and score_batch_async returns Ok(vec![]) — a genuinely empty input is different from Lesson 19's ScoringError::EmptyWindow, which means the scorer's own sliding window has no samples after eviction, not that the caller sent a short batch.

let scores = try await scorer.scoreBatchAsync(shardLabel: "shard-42", values: samples, timestampsUnixMs: timestamps)

Part 3: Swift 6 and the partial-Sendable caveat

⚠️
Swift 6's data-race checking rolls out module by module

Swift's own migration guide describes enabling complete data-race safety checking incrementally, one module at a time, rather than as an all-or-nothing switch. Types generated by UniFFI for the Pulsewatch scoring API are not automatically, fully Sendable-verified against Swift 6's strict concurrency model — treat cross-boundary concurrency claims for generated bindings as something to verify per type, not assume.

In practice: keep the generated Pulsewatch Swift API's async entry points behind a small isolation boundary (an actor, or a serial dispatch queue) until each crossed type has been explicitly checked under Swift 6's strict-concurrency build settings.

Part 4: building an XCFramework from three cargo targets

iOS apps run on-device (arm64) and in the Simulator (both Apple Silicon and Intel hosts), so the same Rust crate must be built three times and merged into one distributable framework bundle. UniFFI's own tutorial is explicit that generate --library reads the bindings' metadata out of a cdylib built for the library — and a cross-compiled iOS artifact is never loadable by the host uniffi-bindgen process, whether it is a staticlib or a dylib. That means two separate build outputs, for two separate purposes: a host cdylib purely to generate Swift source from, and the real iOS staticlibs that ship inside the XCFramework. This is the same crate that shipped the Android .so in Lesson 21, so its crate-type, dependencies, and uniffi::setup_scaffolding!() call are already in place from that lesson — recapped here only for reference, not introduced fresh:

# crates/pulsewatch-scoring/Cargo.toml -- unchanged from Lesson 21, Part 4

[dependencies]
uniffi = { version = "0.32", features = ["cli"] }

[[bin]]
name = "uniffi-bindgen"
path = "uniffi-bindgen.rs"

Part 5: SwiftPM binaryTarget, signing, and who owns what

📦
UniFFI generates bindings; it does not package or sign anything

UniFFI's own documentation is explicit that it produces the Swift binding source and the C scaffolding it depends on — assembling the XCFramework, wiring SwiftPM, and code signing all remain the app team's responsibility, exactly as with the Kotlin/Android packaging step in Lesson 21.

A SwiftPM binaryTarget can only vend a precompiled artifact — the XCFramework built in Part 4 — it cannot compile the generated pulsewatch_scoring.swift source itself. That file needs an ordinary source target that depends on the binary target, pointed at the exact directory Part 4's cp step copied the generated source into. A testTarget is included too, so this package can validate itself end to end without depending on any separate app project or manually configured Xcode scheme — Xcode derives a test-runnable scheme named after this package automatically from Package.swift itself. File: path/to/pulsewatch/Package.swift (new file, complete):

// swift-tools-version:5.9
import PackageDescription

let package = Package(
    name: "PulsewatchScoring",
    platforms: [.iOS(.v15)], // the XCFramework only ships iOS device/simulator slices
    products: [
        .library(name: "PulsewatchScoring", targets: ["PulsewatchScoring"]),
    ],
    targets: [
        // The precompiled XCFramework from Part 4 -- binary only, no source.
        .binaryTarget(
            name: "PulsewatchScoringFFI",
            path: "PulsewatchScoringFFI.xcframework"
        ),
        // The uniffi-bindgen-generated Swift source, copied here by Part 4's
        // cp step, wrapping the binary target.
        .target(
            name: "PulsewatchScoring",
            dependencies: ["PulsewatchScoringFFI"],
            path: "Sources/PulsewatchScoring" // contains pulsewatch_scoring.swift
        ),
        // Exercises MobileScorer through the generated Swift bindings --
        // this is what Part 6's exercise actually runs.
        .testTarget(
            name: "PulsewatchScoringTests",
            dependencies: ["PulsewatchScoring"],
            path: "Tests/PulsewatchScoringTests"
        ),
    ]
)

App code depends on the PulsewatchScoring product — the source target — never directly on PulsewatchScoringFFI. Apple's packaging documentation describes a binaryTarget pointing at a local or remote XCFramework, and separately documents notarizing macOS software before distribution — for iOS-only frameworks embedded in an app, Xcode's normal app-signing step covers the framework, but any macOS-distributed binary needs the explicit notarization flow.

import XCTest
import PulsewatchScoring

final class PulsewatchScoringTests: XCTestCase {
    func testScoresFortySamplesWithoutCrashing() throws {
        let scorer = try MobileScorer(baselineWindowSecs: 300.0, sensitivity: 0.62)
        var scored = 0
        var t: Int64 = 1_758_067_200_000

        // Warm-up: the first sample only seeds the baseline window
        // (Lesson 19's EmptyWindow rule) and is expected to throw.
        do {
            _ = try scorer.score(shardLabel: "fleet-a", value: 100.0, timestampUnixMs: t)
            XCTFail("expected emptyWindow on the warm-up sample")
        } catch MobileScoringError.emptyWindow {
            // expected exactly once, for the warm-up sample
        }

        for i in 0..<40 {
            t += 1_000
            let value = (i == 20) ? 500.0 : 100.0
            _ = try scorer.score(shardLabel: "fleet-a", value: value, timestampUnixMs: t)
            scored += 1
        }

        XCTAssertEqual(scored, 40)
        print("scored \(scored)/40 offline samples on iOS, 0 crashes")
    }
}

Knowledge check

1. Why does UniFFI's Swift support rely on the same kind of C-compatible foundation as Lesson 19's raw ABI?

Answer: Rust's own ABI and layout are not a stable foreign contract, so every language binding — C, Kotlin, or Swift — has to cross through a deliberately narrow, stable scaffolding layer instead of relying on Rust's internal representation directly.

2. Should generated Pulsewatch Swift types be assumed fully Sendable-safe under Swift 6?

Answer: No. Swift 6's data-race checking is enabled incrementally per module, so generated bindings need to be checked per type under strict concurrency rather than assumed safe by default.

3. Why are three separate cargo build --target invocations needed before xcodebuild -create-xcframework?

Answer: Device and Simulator use different architectures/ABIs (device arm64, Simulator arm64 and x86_64), so the crate must be compiled once per target and the two Simulator slices merged with lipo before assembling the XCFramework.

4. Why does generating the Swift bindings need a separate host cargo build --release, instead of reading metadata straight from one of the iOS static libraries built for the XCFramework?

Answer: uniffi-bindgen generate --library reads its metadata from a cdylib the host machine can load; an iOS-target build, static or dynamic, is cross-compiled for a different architecture/ABI and is never loadable by the host process running the tool. The host cdylib exists purely to generate bindings from — the iOS staticlibs, built separately, are what actually ship inside the XCFramework.

5. Can a SwiftPM binaryTarget directly contain the generated pulsewatch_scoring.swift source file, and does UniFFI assemble or sign the XCFramework for you?

Answer: No to both. A binaryTarget only vends a precompiled artifact (the XCFramework); the generated Swift source needs an ordinary source target that depends on it. UniFFI itself only generates the Swift binding source and C scaffolding — assembling the XCFramework, wiring the two SwiftPM targets, and code signing all remain the app team's responsibility.

6. Does the generated Swift MobileScorer need an explicit .close() call the way Lesson 21's Kotlin binding does?

Answer: No. UniFFI represents a Swift object as a concrete class holding a reference to the underlying Rust object; ordinary Swift ARC releases that reference through the class's deinit once the last reference goes out of scope. Kotlin needs an explicit close() specifically because the JVM lacks a reliable, timely finalizer — Swift's deterministic reference counting does not have that gap.

Recap: migration decision rubric

Across Lessons 19-22, one repeatable rubric applies whenever a C++ module needs a foreign caller:

  1. Characterize before you translate. Capture existing behavior with characterization tests (Lesson 19) so any port has a pass/fail oracle.
  2. Choose the narrowest seam that solves the real problem. A wider seam is not automatically better; it's more ABI surface to keep stable.
  3. Translate invariants and ownership deliberately, not mechanically. No tool surveyed in this course (bindgen, cxx, autocxx, Crubit, UniFFI) claims full, automatic conversion of arbitrary C++ or Rust semantics.
  4. Match the tool to the boundary, not the other way around. Raw extern "C" for a minimal stable contract; cxx for a rich bidirectional native bridge; UniFFI for a mobile product API in Kotlin or Swift.
  5. Verify tool status before you depend on it. autocxx now points new users elsewhere; Crubit and UniFFI both publish their own coverage gaps — check them per use case.
  6. Prove parity continuously. Differential and characterization tests (Lesson 19) stay in the suite after the port, not just during it.
  7. Roll out staged, with a real rollback path. Canary, ramp, flag-flip rollback, and only delete the legacy path after a full soak — the same discipline whether the new caller is C, Kotlin, or Swift.
