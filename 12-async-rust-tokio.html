Lesson 12 · 30 minutes

Async Rust and the Tokio Runtime

Move Pulsewatch's scheduler onto Tokio so hundreds of probes run concurrently on a handful of threads, while Lesson 11's blocking protocol code keeps working unchanged behind spawn_blocking.

By the end: You can explain what async fn and .await really compile to, why a future must be Send and often 'static to be spawned, how to bridge blocking code into an async runtime with spawn_blocking, and how to bound concurrency and cancel slow probes safely with Tokio's channels, select!, and timeouts.

Part 1: an async fn builds a paused state machine, it does not run one

Lesson 11's probe_once blocks the calling thread for the whole round trip. Calling it once per target, one thread per target, is exactly the thread-per-connection ceiling Lesson 11 warned about. Async Rust exists to run many waiting-on-I/O operations on a small, fixed pool of OS threads.

This lesson's async code builds toward one new file, crates/pulsewatch-cli/src/async_probe.rs, alongside Lesson 11's tcp_probe.rs in the same pulsewatch-cli package. Parts 1 through 4 below are excerpts that explain one function at a time; the exercise in Part 5 gives that file's complete, exact contents to create, plus a new dependency line and a new binary.

Excerpt from crates/pulsewatch-cli/src/async_probe.rs (illustrates the shape of an async probe function; the exercise gives the complete file):

async fn probe_once_async(
    host: String,
    port: u16,
    timeout: std::time::Duration,
) -> std::io::Result<pulsewatch_core::ProbeOutcome> {
    use tokio::io::{AsyncReadExt, AsyncWriteExt, BufReader};
    use tokio::net::TcpStream;
    use tokio::time::Instant;

    let target = format!("{host}:{port}");
    let started = Instant::now();

    let stream = tokio::time::timeout(timeout, TcpStream::connect(&target)).await??;
    let (reader, mut writer) = stream.into_split();
    let mut reader = BufReader::new(reader);

    writer.write_all(b"PING pulsewatch-v1\n").await?;

    let mut line = String::new();
    tokio::time::timeout(
        timeout,
        tokio::io::AsyncBufReadExt::read_line(&mut reader, &mut line),
    )
    .await??;

    let latency_ms = started.elapsed().as_millis();
    Ok(pulsewatch_core::ProbeOutcome {
        target,
        success: line.trim_end().starts_with("PONG"),
        latency_ms,
        message: line.trim_end().to_string(),
    })
}

Calling probe_once_async(...) does not connect to anything yet. It returns a value implementing Future: a paused state machine capturing host, port, and timeout, with one variant per suspension point. Only .await, driven by a runtime, advances that state machine toward a result.

Rust syntaxMeaningC++ bridge
async fn f(...) -> TCompiles to a function returning impl Future<Output = T>: an anonymous state-machine type, not a thread and not immediate execution.Structurally closest to a hand-written std::coroutine or a resumable-function transform; more distant from std::future, which represents an already-scheduled asynchronous result.
.awaitA suspension point: if the inner future is not ready, control returns to the runtime, which polls other tasks; when ready, execution resumes right here.Similar in intent to co_await on a C++20 awaitable, including that the compiler transforms the function into a state machine around each suspension point.
tokio::time::timeout(dur, fut).awaitRaces fut against a timer; returns Ok(fut's output) or Err(Elapsed), and drops fut if the timer wins.No direct equivalent; closest to combining a deadline-based cancellation token with a wait on a future/promise pair.
stream.into_split()Splits an owned, connected socket into an owned read half and an owned write half that can live in different tasks.The async analogue of Lesson 11's try_clone, but returning two distinct owned types instead of two handles to the same duplicated descriptor.

Part 2: the runtime, tasks, and why futures must be Send

A future by itself never runs. Tokio's runtime is the executor: it owns a thread pool, polls spawned futures when they are woken, and drives timers and I/O readiness.

Excerpt only (a standalone main shown to explain #[tokio::main] and tokio::spawn; the exercise's async_probe.rs does not include a main function, since it is a library module, not a binary):

#[tokio::main]
async fn main() {
    let handle = tokio::spawn(probe_once_async(
        "127.0.0.1".to_string(),
        7878,
        std::time::Duration::from_secs(2),
    ));

    match handle.await {
        Ok(Ok(outcome)) => println!("{} -> success={} ({} ms)", outcome.target, outcome.success, outcome.latency_ms),
        Ok(Err(io_err)) => eprintln!("probe failed: {io_err}"),
        Err(join_err) => eprintln!("probe task panicked: {join_err}"),
    }
}
Rust syntaxMeaningC++ bridge
#[tokio::main]Macro that wraps main so it builds a multi-threaded Tokio runtime and blocks on the async body until it completes.Roughly equivalent to hand-writing runtime.block_on(async_main()) with an explicit thread pool created first.
tokio::spawn(fut)Hands the future to the runtime as an independent task; it may run concurrently with the caller and other tasks. Returns a JoinHandle.Closer to submitting a unit of work to a thread pool's task queue than to creating an OS thread directly.
handle.awaitWaits for the spawned task to finish, yielding Result<T, JoinError> — an outer error only for task panics or cancellation, wrapping the task's own Result.Similar to joining a future/promise pair where the join itself can fail independently of the computed value.
fut: Future + Send + 'statictokio::spawn requires the future to be safely movable to another thread (Send) and to own everything it touches with no borrowed lifetime shorter than the task ('static).Analogous to requiring a task submitted to a thread pool to not capture references to stack locals that could be destroyed before the task runs — except the compiler enforces it rather than a code reviewer.
⚠️
Send and 'static are not paperwork

A future that holds a non-Send type (for example, an Rc<T> instead of Arc<T>) across an .await point fails to compile under tokio::spawn. That rejection is the compiler catching, ahead of time, a bug that in C++ would surface as a data race the first time the task actually migrated threads.

Part 3: bridging Lesson 11's blocking code with spawn_blocking

Pulsewatch does not have to rewrite everything at once. Lesson 11's probe_once, in crates/pulsewatch-cli/src/tcp_probe.rs, is still correct; it simply must never run directly on a Tokio worker thread, because a blocking call there stalls every other task scheduled onto that thread. Because async_probe.rs and tcp_probe.rs are sibling modules in the same pulsewatch-cli crate, the bridge below reaches probe_once through crate::tcp_probe::probe_once, not through a separate crate name.

Excerpt from crates/pulsewatch-cli/src/async_probe.rs (the blocking-bridge function; the exercise gives the complete file):

async fn probe_once_legacy(
    host: String,
    port: u16,
    timeout: std::time::Duration,
) -> std::io::Result<pulsewatch_core::ProbeOutcome> {
    tokio::task::spawn_blocking(move || {
        crate::tcp_probe::probe_once(&host, port, timeout)
    })
    .await
    .expect("blocking probe task panicked")
}
Rust syntaxMeaningC++ bridge
tokio::task::spawn_blocking(closure)Runs closure on a separate pool of blocking-capable threads instead of the async worker threads, returning a JoinHandle whose output is the closure's return value.Comparable to offloading blocking work to a dedicated thread pool distinct from the async reactor's threads, a pattern many C++ event-loop frameworks require by hand.
move || { probe_once(...) }The closure owns host, port, and timeout outright, satisfying the same Send + 'static requirement as a spawned future.Same discipline as ensuring a task queued to a background thread pool does not capture references to caller-local state.
.await.expect(...)Waits for the blocking task and unwraps the JoinHandle's outer Result, which only reports a panic in the closure, distinct from the inner io::Result.Similar to checking a future's exceptional-completion path separately from its normal return value.

This gives Pulsewatch a deliberate migration seam: new probe kinds are written as native async fns against tokio::net, while any legacy blocking probe keeps running correctly, quarantined onto the blocking-thread pool, until someone chooses to rewrite it.

Part 4: racing work with select!, and what cancellation safety means

Excerpt from crates/pulsewatch-cli/src/async_probe.rs (the shutdown-racing function; the exercise gives the complete file):

use tokio::sync::mpsc;

async fn probe_with_shutdown(
    host: String,
    port: u16,
    timeout: std::time::Duration,
    mut shutdown: mpsc::Receiver<()>,
) -> Option<std::io::Result<pulsewatch_core::ProbeOutcome>> {
    tokio::select! {
        outcome = probe_once_async(host, port, timeout) => Some(outcome),
        _ = shutdown.recv() => None,
    }
}

select! polls every listed branch and proceeds with whichever future completes first, immediately dropping the others. That drop is why cancellation safety matters: probe_once_async above never partially mutates any state that would be observed later, so being dropped mid-flight (for example, after connecting but before reading a reply) simply discards the in-flight connection cleanly. A future that had, say, already removed an item from a queue before its next .await would lose that item silently if cancelled at the wrong point — a real hazard Tokio's own documentation calls out by name.

Rust syntaxMeaningC++ bridge
tokio::select! { a => ..., b => ... }Concurrently polls each branch's future; the first to complete wins, and the rest are dropped without further polling.Loosely comparable to a manually written select(2)/epoll_wait readiness race, but operating over arbitrary futures rather than raw file descriptors.
mpsc::Receiver<()>The receiving half of an async multi-producer, single-consumer channel; () as the payload makes this purely a shutdown signal.Similar to a condition-variable-guarded flag used to signal a worker to stop, but delivered as a message a task .awaits instead of a variable it polls.
Cancellation safetyA future is cancellation-safe if being dropped at any .await point leaves no half-applied side effect that would corrupt later state.Analogous to strong exception safety: an operation interrupted partway through must leave the system in a valid, well-understood state.

Part 5: exercise — bound Pulsewatch's concurrency and collect results

Probing every target with an unbounded tokio::spawn per target risks opening thousands of sockets at once against a target that cannot handle that load. This exercise creates the complete async_probe.rs file — combining Parts 1 through 4's excerpts with a concurrency-bounding scheduler — plus the dependency and binary needed to run it.   1. Append to crates/pulsewatch-cli/Cargo.toml under its existing [dependencies] table (do not remove the existing pulsewatch-core path dependency already there from Lesson 7):

    This declares tokio as a direct dependency of pulsewatch-cli because #[tokio::main], tokio::spawn, and the other tokio:: paths below are named directly in this crate's own source, not merely reached transitively through another crate.

  2. Append to crates/pulsewatch-cli/src/lib.rs (this file already exists from Lesson 11 with pub mod tcp_probe;; add one more line below it, do not remove the existing one):

pub mod async_probe;
  3. Create crates/pulsewatch-cli/src/async_probe.rs with exactly this content — it combines the four Part 1–4 excerpts into one file and adds the bounded scheduler and its test: 
    // crates/pulsewatch-cli/src/async_probe.rs
use std::sync::Arc;
use tokio::io::{AsyncBufReadExt, AsyncWriteExt, BufReader};
use tokio::net::TcpStream;
use tokio::sync::{mpsc, Semaphore};
use tokio::time::Instant;

pub async fn probe_once_async(
    host: String,
    port: u16,
    timeout: std::time::Duration,
) -> std::io::Result<pulsewatch_core::ProbeOutcome> {
    let target = format!("{host}:{port}");
    let started = Instant::now();

    let stream = tokio::time::timeout(timeout, TcpStream::connect(&target)).await??;
    let (reader, mut writer) = stream.into_split();
    let mut reader = BufReader::new(reader);

    writer.write_all(b"PING pulsewatch-v1\n").await?;

    let mut line = String::new();
    tokio::time::timeout(timeout, reader.read_line(&mut line)).await??;

    let latency_ms = started.elapsed().as_millis();
    Ok(pulsewatch_core::ProbeOutcome {
        target,
        success: line.trim_end().starts_with("PONG"),
        latency_ms,
        message: line.trim_end().to_string(),
    })
}

pub async fn probe_once_legacy(
    host: String,
    port: u16,
    timeout: std::time::Duration,
) -> std::io::Result<pulsewatch_core::ProbeOutcome> {
    tokio::task::spawn_blocking(move || crate::tcp_probe::probe_once(&host, port, timeout))
        .await
        .expect("blocking probe task panicked")
}

pub async fn probe_with_shutdown(
    host: String,
    port: u16,
    timeout: std::time::Duration,
    mut shutdown: mpsc::Receiver<()>,
) -> Option<std::io::Result<pulsewatch_core::ProbeOutcome>> {
    tokio::select! {
        outcome = probe_once_async(host, port, timeout) => Some(outcome),
        _ = shutdown.recv() => None,
    }
}

pub async fn run_scheduler(
    targets: Vec<(String, u16)>,
    max_concurrent: usize,
    timeout: std::time::Duration,
) -> Vec<std::io::Result<pulsewatch_core::ProbeOutcome>> {
    let semaphore = Arc::new(Semaphore::new(max_concurrent));
    let (tx, mut rx) = mpsc::channel(targets.len().max(1));

    for (host, port) in targets {
        let semaphore = Arc::clone(&semaphore);
        let tx = tx.clone();
        tokio::spawn(async move {
            let _permit = semaphore
                .acquire()
                .await
                .expect("semaphore is never closed while tasks run");
            let result = probe_once_async(host, port, timeout).await;
            let _ = tx.send(result).await;
        });
    }
    drop(tx);

    let mut results = Vec::new();
    while let Some(result) = rx.recv().await {
        results.push(result);
    }
    results
}

#[cfg(test)]
mod tests {
    use super::*;

    #[tokio::test]
    async fn scheduler_bounds_concurrency_and_collects_all_results() {
        let targets = vec![
            ("127.0.0.1".to_string(), 7878),
            ("127.0.0.1".to_string(), 7879),
            ("127.0.0.1".to_string(), 7880),
        ];
        let results = run_scheduler(targets, 2, std::time::Duration::from_millis(500)).await;
        assert_eq!(results.len(), 3);
    }
}

    Semaphore::new(max_concurrent) caps the number of probes in flight at once regardless of how many targets exist, preventing a socket or file-descriptor storm; the permit is released automatically when _permit is dropped at the end of the async block. mpsc::channel(targets.len().max(1)) gives every spawned task its own cloned sender, and drop(tx) drops the scheduler's own sender so rx.recv() returns None, ending the collection loop, once every cloned sender has also been dropped.

    // crates/pulsewatch-cli/src/bin/pulsewatch-scheduler.rs
#[tokio::main]
async fn main() {
    let args: Vec<String> = std::env::args().collect();
    let max_concurrent: usize = flag_value(&args, "--max-concurrent")
        .unwrap_or_else(|| "10".to_string())
        .parse()
        .expect("--max-concurrent must be a positive integer");
    let targets_path = flag_value(&args, "--targets").expect("--targets PATH is required");

    let contents = std::fs::read_to_string(&targets_path).expect("read targets file");
    let targets: Vec<(String, u16)> = contents
        .lines()
        .filter(|line| !line.trim().is_empty())
        .map(|line| {
            let (host, port) = line.trim().split_once(':').expect("expected host:port");
            (host.to_string(), port.parse().expect("port must be a u16"))
        })
        .collect();

    let results = pulsewatch_cli::async_probe::run_scheduler(
        targets,
        max_concurrent,
        std::time::Duration::from_secs(2),
    )
    .await;

    for result in results {
        match result {
            Ok(outcome) => println!("{outcome:?}"),
            Err(io_err) => eprintln!("probe failed: {io_err}"),
        }
    }
}

fn flag_value(args: &[String], name: &str) -> Option<String> {
    args.iter().position(|a| a == name).and_then(|i| args.get(i + 1)).cloned()
}

What actually changed, and what did not

The Pulsewatch probe protocol from Lesson 11 — the PING/PONG framing, the timeout discipline, the loopback test strategy — is unchanged, and tcp_probe.rs itself is not modified in this lesson. What changed is the scheduler: instead of one OS thread per target, a small pool of Tokio worker threads cooperatively multiplexes hundreds of in-flight probes, each suspended on .await rather than blocked on a syscall.

Knowledge check

1. What does calling an async fn actually produce, and when does its body start running?

Answer: It produces a value implementing Future — a paused state machine capturing its arguments and locals. No code in the body runs until that future is polled, which happens when it is .awaited inside a running task or spawned onto a runtime.

2. Why must a future passed to tokio::spawn be Send + 'static?

Answer: Tokio's multi-threaded runtime may move a spawned task between worker threads while it runs, so anything the future holds must be safe to send across threads (Send) and must not borrow data that could be dropped before the task finishes ('static). The compiler rejects a future that violates either bound at the spawn call site.

3. Why does Lesson 11's probe_once need spawn_blocking rather than being called directly inside an async fn?

Answer: probe_once blocks its calling thread for the whole round trip using OS-level blocking I/O. Calling it directly on a Tokio worker thread would stall every other task scheduled onto that same thread. spawn_blocking moves it onto a separate pool of threads dedicated to blocking work.

4. What does it mean for probe_once_async to be cancellation-safe inside a select! branch?

Answer: If the branch is dropped mid-flight because another branch of the select! completed first, no partially applied state is left behind: the in-flight connection is simply closed, and nothing has been recorded as succeeded or consumed that should not have been.

Recap and decision rules

Waiting on I/O, want to scale past a thread per target?  Use async fn / .await and a runtime
Need to run a future concurrently with others?             tokio::spawn(fut) -> JoinHandle
Have existing blocking code that still works?               tokio::task::spawn_blocking(closure)
Racing two operations, first one wins?                      tokio::select! { ... }
Need a deadline on an operation?                             tokio::time::timeout(dur, fut)
Fan-out with a concurrency cap?                              Arc<Semaphore> + acquire().await
Collecting results from many spawned tasks?                  tokio::sync::mpsc channel, drain the receiver
Future captures non-Send state across .await?                Compiler rejects spawn; fix ownership, don't fight it
