Lesson 17 · 30 minutes

Debugging & Observability

Diagnose a Pulsewatch failure with backtraces, LLDB/GDB, panic hooks, typed errors, and structured tracing, without leaking secrets or confusing debug-build behavior with release.

By the end: you can distinguish rust-analyzer diagnostics from a real compiler check, capture and read a backtrace, attach LLDB or GDB to a Rust binary, choose between thiserror and anyhow at the right boundary, add tracing spans and a subscriber, and avoid logging secrets or high-cardinality data.

Follow-along setup

This lesson starts from the Pulsewatch workspace as Lessons 7–16 left it: crates/pulsewatch-core (the Probe trait and types), and crates/pulsewatch-service, the Axum binary from Lesson 13 that Lesson 15 extended with SQLx persistence and AppConfig. This lesson adds error types, a panic hook, and tracing to that existing binary; it does not remove anything.

cd path/to/pulsewatch

path/to is a placeholder: replace the whole segment with wherever you checked out the Pulsewatch workspace, for example cd ~/dev/pulsewatch. Unless a step says otherwise, run every cargo command below from this workspace root, the directory containing the top-level Cargo.toml. The debugger session in Part 2 additionally requires rust-lldb (bundled with a standard rustup-installed toolchain) or rust-gdb on Linux.

Part 1: rust-analyzer, compiler diagnostics, and backtraces

rust-analyzer's red squiggles are a fast, incremental approximation running inside the editor; the real source of truth is still cargo check, which runs the actual compiler front end. When rust-analyzer and cargo check disagree (stale index, macro-heavy code, cross-crate changes), trust cargo check. When something panics, ask for a stack trace before guessing. Run both commands from the workspace root:

RUST_BACKTRACE=1 cargo run -p pulsewatch-service
RUST_BACKTRACE=full cargo run -p pulsewatch-service   # includes library-internal frames

You can also capture a backtrace programmatically, useful when converting a panic into a structured log line. This line belongs inside the panic hook you add in Part 3:

crates/pulsewatch-service/src/main.rs — excerpt (used inside the panic hook added in Part 3, not a separate edit)
let backtrace = std::backtrace::Backtrace::capture();
tracing::error!(%backtrace, "unexpected panic captured");

Part 2: a debugger session with LLDB or GDB

Rust ships thin wrappers, rust-lldb and rust-gdb, that pretty-print Rust types (Vec, String, enums) inside the same LLDB/GDB you already know from C++. Build the server, run it under the debugger, set a breakpoint on a handler the running server actually calls (check_target, from Lesson 13), then trigger that handler from another terminal with curl:

cargo build -p pulsewatch-service
rust-lldb target/debug/pulsewatch-service
(lldb) breakpoint set --name check_target
(lldb) run
# in a second terminal, from anywhere: curl http://127.0.0.1:8080/check/example.com
(lldb) print url
(lldb) bt
(lldb) continue

The commands are the same ones you already use for C++: set a breakpoint, run, print a value, unwind the stack, continue. The only new thing is that Rust's richer pretty-printers show a Rust String or Vec as a real value instead of a raw pointer and length.

Part 3: panic hooks and typed error boundaries

A custom panic hook lets you route every panic through your own logging instead of only stderr:

crates/pulsewatch-service/src/main.rs — append near the top of fn main, before serve() is called
std::panic::set_hook(Box::new(|info| {
    tracing::error!(panic = %info, "pulsewatch-service panicked");
}));

For recoverable failures, Rust draws a boundary between library and application error handling. thiserror derives a concrete, typed error enum at a library boundary such as pulsewatch-core, so callers can match on a variant; anyhow is for the application's main, where you mostly want to attach context and propagate, not match on variants.

crates/pulsewatch-core/src/error.rs — create (then add `mod error; pub use error::PersistError;` to crates/pulsewatch-core/src/lib.rs — append)
// pulsewatch-core: a typed error at the library boundary
#[derive(Debug, thiserror::Error)]
pub enum PersistError {
    #[error("database unavailable: {0}")]
    Unavailable(#[source] sqlx::Error),
    #[error("row violated a constraint: {0}")]
    Constraint(String),
}
crates/pulsewatch-service/src/main.rs — append
// pulsewatch-service/src/main.rs: anyhow at the application boundary
fn load_config() -> anyhow::Result<AppConfig> {
    AppConfig::from_env().context("failed to load Pulsewatch configuration")
}

Part 4: structured observability with tracing

tracing replaces scattered println! calls with structured, leveled spans and events that a subscriber can filter, format, or export:

crates/pulsewatch-service/src/main.rs — append near the top of fn main, before the panic hook and before serve()
use tracing_subscriber::{fmt, EnvFilter};

fn init_observability() {
    tracing_subscriber::registry()
        .with(EnvFilter::from_default_env())
        .with(fmt::layer())
        .init();
}

The function below shows the #[tracing::instrument] pattern on a simplified record_batch(pool, samples: &[Sample]) signature for illustration; apply the same #[tracing::instrument(skip(pool))] attribute and tracing::info! call to the real record_batch in crates/pulsewatch-service/src/db.rs from Lesson 15, whose parameters are pool: &SqlitePool, target_id: i64, outcomes: &[ProbeOutcome]:

crates/pulsewatch-service/src/db.rs — replace the existing record_batch signature line and its first statement (add the attribute and the info! line shown here; the rest of the function body is unchanged from Lesson 15)
#[tracing::instrument(skip(pool))]
async fn record_batch(pool: &SqlitePool, samples: &[Sample]) -> Result<(), PersistError> {
    tracing::info!(count = samples.len(), "recording sample batch");
    // ...
    Ok(())
}

#[tracing::instrument] wraps a whole async function in a span, so every event inside it, and any spans it enters, are automatically tagged with the function's name and arguments (unless explicitly skipped, as pool is here).

⚠️
Do not instrument secrets or high-cardinality data

#[tracing::instrument] captures every non-skipped argument by default. Skip database URLs, tokens, and any field that is effectively unique per record (raw sample payloads, full request bodies); log a count, a hash, or a bucketed value instead. A field logged once in a test fixture can end up in production log output the first time this code path runs there.

Part 5: debug builds are not release behavior

Debug builds enable overflow checks and debug_assert!; release builds optimize and, by default, still keep debug symbols on many platforms unless stripped. A bug that only reproduces in release is often an overflow check or an assertion that silently no-ops there — do not assume debug-build behavior generalizes:

Cargo.toml (workspace root) — append (profile sections apply only from the root Cargo.toml of a virtual workspace, not from a member crate's Cargo.toml)
[profile.release]
debug = true       # keep symbols for profiling/debugging without disabling optimizations
# strip = true     # would remove symbols again; leave unset while you still need them

Read the Rust: syntax mapped to C++

RustMeaningC++ bridge
RUST_BACKTRACE=fullPrints a full stack trace, including library-internal frames, on panic.Comparable to running under a debugger just to capture a crash's call stack.

Worked Pulsewatch increment

Pulsewatch now has structured, leveled logs from every async handler via #[tracing::instrument], a typed PersistError at the pulsewatch-core boundary that anyhow::Context annotates in main, a panic hook that routes crashes through the same subscriber as everything else, and a documented LLDB workflow for attaching to pulsewatch-service when a report alone is not enough.

🧭
Stability and production boundary

A panic hook, typed errors, and tracing spans make failures easier to diagnose; they do not prevent failures, and a debug build's overflow checks and debug_assert!s do not run in release, so a bug that only reproduces under --release needs to be reproduced there, not assumed away from a debug-build repro.

Knowledge check

1. rust-analyzer and cargo check disagree about whether a function compiles. Which do you trust, and why?

Answer: cargo check, because it runs the real compiler front end; rust-analyzer is a fast incremental approximation that can lag behind on macro-heavy or cross-crate changes.

2. When should a Pulsewatch function return a thiserror-derived enum instead of an anyhow::Result?

Answer: At a library boundary, such as pulsewatch-core, where callers need to match on a specific error variant; anyhow is for application-level code in main that mostly needs to attach context and propagate.

3. Why should you skip a database URL or raw sample payload from #[tracing::instrument] instead of letting it log by default?

Answer: Instrument captures every non-skipped argument by default; secrets should never be logged, and high-cardinality or unique-per-record data bloats and de-values log output, so both should be skipped, counted, or hashed instead.

4. A bug reproduces in debug builds but not in --release. What is the first thing to check?

Answer: Whether the bug depends on debug-only behavior such as overflow checks or debug_assert!, which do not run in release; reproduce and diagnose it under --release rather than assuming the debug-build repro generalizes.

Recap and decision rules

Unexpected panic, need the call stack?         RUST_BACKTRACE=full, or capture programmatically
Need to inspect live state under a breakpoint?  rust-lldb / rust-gdb, same workflow as C++
Library-boundary error callers must match on?   thiserror-derived enum
Application-level error that just needs context? anyhow::Result + .context(...)
Want every event auto-tagged with a function?    #[tracing::instrument]
About to log a secret or unique-per-record value? Skip it, or log a count/hash instead
Bug only reproduces in release?                 Debug-only checks are off; verify under --release
