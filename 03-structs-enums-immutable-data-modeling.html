Lesson 3 · 30 minutes

Structs, Enums, Methods, and Immutable Data Modeling

Rust has no class keyword and no record type. Data lives in structs and enums; behavior lives in impl blocks. Build a real GreeterConfig for rust-greeter using exactly that shape.

By the end: You can state plainly why Rust has no classes or records, define named/tuple/unit structs and methods, model a closed set of alternatives with an enum, and explain the idiomatic way to get record-like, invariant-protecting data without a dedicated "readonly" type.

Part 1: no classes, no record

This needs to be said directly, because looking for the familiar keyword wastes time: Rust has no class keyword and no record keyword or type. There is no built-in inheritance-based type either. Instead, Rust splits the two things a C++ class bundles together:

C++ conceptRust equivalent
class/struct — data and member functions togetherstruct or enum for data; a separate impl block for its methods and associated functions
record-style value type with generated equality/copyingA plain struct plus #[derive(...)] for the specific behaviors you want (Part 3)
Interfaces / abstract base classesTraits — covered in depth in Lesson 6, previewed briefly here through #[derive(Debug)]
Class hierarchy / virtual dispatchNo inheritance between structs at all; shared behavior comes from traits, and enums model closed sets of variants (Part 5)

Part 2: named, tuple, and unit structs

A named struct has labeled fields, closest to a C++ struct or class's data members. It carries #[derive(Clone)] here so the struct-update-syntax example below it can call .clone() explicitly — derives themselves are covered in Part 3:

struct RepeatCount(u8); // tuple struct — see below

#[derive(Clone)]
struct GreeterConfigPreview {
    name: String,
    greeting_count: u8,
}

fn build() {
    let count = 3;
    let config = GreeterConfigPreview {
        name: String::from("Ada"),
        greeting_count: count, // field init shorthand needs `greeting_count: count`
    };
    println!("{} x{}", config.name, config.greeting_count);
}

When a local variable's name exactly matches a field's name, you can drop the repetition — field init shorthand:

let greeting_count = 3;
let config = GreeterConfigPreview { name: String::from("Ada"), greeting_count };
//                                                              ^^^^^^^^^^^^^^ shorthand for `greeting_count: greeting_count`

A tuple struct like struct RepeatCount(u8); above wraps a single value in a distinct named type — a "newtype" — so a RepeatCount can never be confused with an unrelated u8 at a function boundary, even though both are plain numbers underneath. A unit struct like struct Marker; carries no data at all; it exists purely as a distinct type, often to implement a trait against.

Struct update syntax (..base) copies any fields you did not explicitly override from an existing value — but for non-Copy fields, this moves them out of base, just like Lesson 2's tuple assignment:

Rejected: base reused after its name moved
let base = GreeterConfigPreview { name: String::from("Ada"), greeting_count: 1 };
let formal = GreeterConfigPreview { greeting_count: 2, ..base };
println!("{}", base.name); // error[E0382]: borrow of
                            // partially moved value: `base`
Works: clone first if you still need base
let base = GreeterConfigPreview { name: String::from("Ada"), greeting_count: 1 };
let formal = GreeterConfigPreview { greeting_count: 2, ..base.clone() };
println!("{}", base.name); // fine — `base` was never moved from

The left-hand error is real, exact compiler output: partially moving base.name (a String, not Copy) out through ..base leaves base only partially usable, and reading base.name afterward is rejected at compile time — not a runtime surprise.

Part 3: methods, associated functions, visibility, and derives

Methods live in an impl block and take a form of self as their first parameter, which tells you exactly how they interact with the value — something a C++ member function's constness only partially expresses:

ReceiverMeaningClosest C++ analog
&selfBorrows the value to read itconst member function
&mut selfBorrows the value to mutate it in placeNon-const member function
selfTakes ownership — the method consumes the value; the caller's binding becomes unusable afterwardNo exact analog; closest is a function taking an object by value and not giving it back

An associated function has no self parameter at all and is called through the type name, such as GreeterConfig::new(...) — the idiomatic replacement for a C++ constructor:

struct RepeatCount(u8);

impl RepeatCount {
    fn new(requested: u8) -> Self {   // associated function — no `self`
        Self(clamp_repeats(requested)) // `Self` refers to `RepeatCount`
    }

    fn get(&self) -> u8 {           // &self — read-only method
        self.0
    }
}

Every field is private by default, visible only inside the same module unless marked pub. Combined with a constructor that enforces invariants (like clamp_repeats above), this is how Rust achieves encapsulation without a private: section — private-by-default is the baseline, not an opt-in.

#[derive(...)] asks the compiler to generate specific trait implementations mechanically instead of hand-writing them — this is Rust's answer to a C++ "record" auto-generating equality and printing:

DeriveWhat it generates
Debug{:?}-formatting for diagnostics/tests
CloneAn explicit .clone() deep-copy method
CopyBitwise copy instead of move (only legal if every field is Copy, per Lesson 2)
PartialEq==/!= comparison, field by field
💡
The idiomatic "record-like" value

Rust has no distinct deep-readonly record type. The idiom is: private fields, an immutable let config = GreeterConfig::new(...); binding, a constructor that enforces invariants, and read-only accessor methods. Because Rust's owned values (like an owned Vec field) can still be mutated through a &mut accessor if you choose to expose one, "deep immutability" is an API design choice you make by not exposing mutable access — not a property the type system hands you automatically.

Part 4: enums as tagged unions

A C++ enum class is a closed set of named integers with no payload. Rust enums are full algebraic data types: each variant can carry its own distinct payload, and the compiler tracks which variant is active — there is no way to read the wrong payload by accident, unlike a C-style tagged union.

enum Audience {
    Individual,
    Team,
}

enum GreetingStyle {
    Formal,
    Casual,
}

Two standard-library enums replace patterns C++ handles with null pointers and exceptions:

TypeReplaces
Option<T> — Some(T) or NoneA nullable pointer/value, but the compiler forces you to handle the absent case; there is no way to dereference a "null" T by mistake.
Result<T, E> — Ok(T) or Err(E) (preview only; Lesson 5 covers this in depth)Exceptions for recoverable failure. A function that can fail returns Result instead of throwing, and callers must acknowledge the Err case.

match is how you read an enum's active variant, and it is exhaustive: every variant must be handled, or the compiler rejects the code — a preview of Lesson 4's deeper coverage:

fn lookup_style(label: &str) -> Option<GreetingStyle> {
    match label {
        "formal" => Some(GreetingStyle::Formal),
        "casual" => Some(GreetingStyle::Casual),
        _ => None, // required: match must cover every possibility
    }
}

Part 5: evolve rust-greeter to GreeterConfig, Audience, GreetingStyle

File: src/main.rs — add below describe_cast (keep Args, greeting, MAX_REPEATS, APP_NAME, clamp_repeats, and CLAMPED_DEFAULT from Lessons 1–2 unchanged):

#[derive(Debug, Clone, Copy)]
struct RepeatCount(u8);

impl RepeatCount {
    fn new(requested: u8) -> Self {
        Self(clamp_repeats(requested))
    }

    fn get(&self) -> u8 {
        self.0
    }
}

#[derive(Debug, Clone, Copy, PartialEq)]
enum Audience {
    Individual,
    Team,
}

#[derive(Debug, Clone, Copy, PartialEq)]
enum GreetingStyle {
    Formal,
    Casual,
}

fn lookup_style(label: &str) -> Option<GreetingStyle> {
    match label {
        "formal" => Some(GreetingStyle::Formal),
        "casual" => Some(GreetingStyle::Casual),
        _ => None,
    }
}

#[derive(Debug, Clone)]
struct GreeterConfig {
    name: String,
    audience: Audience,
    style: GreetingStyle,
    repeats: RepeatCount,
}

impl GreeterConfig {
    fn new(name: String, audience: Audience, style: GreetingStyle, requested_repeats: u8) -> Self {
        Self {
            name,
            audience,
            style,
            repeats: RepeatCount::new(requested_repeats),
        }
    }

    fn name(&self) -> &str {
        &self.name
    }

    fn describe(&self) -> String {
        format!(
            "{} ({:?}, {:?}, x{})",
            self.name,
            self.audience,
            self.style,
            self.repeats.get()
        )
    }

    fn set_style(&mut self, style: GreetingStyle) {
        self.style = style;
    }

    fn into_name(self) -> String {
        self.name
    }
}

File: src/main.rs — replace fn main from Lesson 2 with:

fn main() {
    let args = Args::parse();
    let audience = if args.name.contains(' ') {
        Audience::Team
    } else {
        Audience::Individual
    };
    let style = lookup_style("casual").unwrap_or(GreetingStyle::Casual);

    let mut config = GreeterConfig::new(args.name.clone(), audience, style, args.count);
    println!("{APP_NAME} config -> {} [{}]", config.describe(), config.name());
    println!(
        "cast demo: {}; compile-time clamped default: {CLAMPED_DEFAULT}",
        describe_cast(1000)
    );

    config.set_style(GreetingStyle::Formal);
    println!("after set_style -> {}", config.describe());

    let repeats = config.repeats.get();
    let owned_name = config.into_name(); // consumes `config`; `config` is unusable after this line
    for _ in 0..repeats {
        println!("{}", greeting(&owned_name));
    }
}
LineWhy it is written this way
let mut config = ...mut is required here because set_style takes &mut self — the binding must opt into mutation, matching Lesson 2's rule.
config.into_name()Takes self by value, so it consumes config. After this line, config can no longer be used — this is the "self" receiver's move-based contract, not a bug.
lookup_style("casual").unwrap_or(...)unwrap_or reads the Some case or falls back to a default for None, avoiding a panic while still using the Option<GreetingStyle> from Part 4 directly.

Knowledge check

1. Why can't you write a Rust class, and what replaces it?

Answer: Rust has no class keyword. Data lives in a struct or enum; its behavior lives in a separate impl block. Shared behavior across types comes from traits (Lesson 6), not inheritance.

2. What is the difference between &self, &mut self, and self as a method receiver?

Answer: &self borrows the value read-only; &mut self borrows it to mutate in place (the binding must be declared mut); self takes ownership, consuming the value so the caller's binding can no longer be used afterward — as with config.into_name().

3. Why does reading base.name after ..base in struct update syntax fail to compile?

Answer: Because name is a String (not Copy), ..base moves it out of base into the new struct. base is left partially moved, and the compiler rejects any later read of the moved field with error E0382. Cloning base first avoids this.

4. How does Rust get record-like, invariant-protecting data without a dedicated "readonly record" type?

Answer: By convention: private fields (the default), a constructor (an associated function like GreeterConfig::new) that enforces invariants such as clamping repeat counts, an immutable binding, and read-only &self accessor methods. Nothing prevents deep mutation if you choose to expose a &mut accessor — immutability is an API design choice, not an automatic guarantee.

Recap and decision rules

Need to bundle related, named data?      Named struct, e.g. `GreeterConfig`
Need a distinct type around one value?   Tuple struct / newtype, e.g. `RepeatCount(u8)`
Need a marker type with no data?         Unit struct, e.g. `struct Marker;`
Need one of several fixed alternatives?  Enum, e.g. `Audience`, `GreetingStyle`
Need "no value" without null pointers?   `Option<T>`
Need "failure" without exceptions?       `Result<T, E>` (deep dive in Lesson 5)
Method only reads the value?             `&self`
Method mutates the value in place?       `&mut self` (binding must be `mut`)
Method should consume/transform once?    `self`

You separated data (struct/enum) from behavior (impl), learned that visibility and constructors — not a special type — give you record-like immutability, and saw match force you to handle every enum variant. Lesson 4 uses this same GreeterConfig inside functions, closures, and macros to actually render greetings by style.
