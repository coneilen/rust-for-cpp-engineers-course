Lesson 14 · 30 minutes

Persisting State with SQLite and rusqlite

Give Pulsewatch a memory: store targets and every probe result in a local SQLite database with rusqlite, using transactions, prepared statements, versioned migrations, and a busy timeout instead of ad-hoc file writes.

By the end: You can open a rusqlite::Connection, run a versioned migration with user_version, insert and query rows with prepared, parameter-bound statements, map SQL NULL to Option<T>, wrap a batch insert in a transaction with correct rollback-on-error behavior, and explain why Connection is confined to one thread.

Part 1: opening a connection that behaves under concurrent access

Every probe result from Lessons 11 through 13 has lived only in memory. This lesson gives Pulsewatch a small SQLite file so targets and history survive a restart, using rusqlite, a safe wrapper over the SQLite C library.

This lesson's persistence code builds toward one new file, crates/pulsewatch-cli/src/store.rs, another sibling module of Lesson 11's tcp_probe.rs, Lesson 12's async_probe.rs, and Lesson 13's http_probe.rs in the same pulsewatch-cli package. Parts 1 through 4 below are excerpts that explain one function at a time; the exercise in Part 5 gives that file's complete, exact contents to create.

Excerpt from crates/pulsewatch-cli/src/store.rs (illustrates opening a connection with WAL, a busy timeout, and foreign keys enabled; the exercise gives the complete file):

use rusqlite::Connection;

pub fn open_store(path: &str) -> rusqlite::Result<Connection> {
    let conn = Connection::open(path)?;
    conn.pragma_update(None, "journal_mode", "WAL")?;
    conn.busy_timeout(std::time::Duration::from_secs(5))?;
    // Unlike journal_mode, foreign_keys is a per-connection setting that
    // SQLite does not persist in the database file, so every connection
    // this function opens must turn it on for itself before use.
    conn.pragma_update(None, "foreign_keys", true)?;
    Ok(conn)
}
Rust syntaxMeaningC++ bridge
Connection::open(path)Opens (creating if absent) a SQLite database file and returns an owned Connection handle wrapping the underlying sqlite3*.Comparable to sqlite3_open wrapped in RAII instead of a raw pointer the caller must remember to close.
pragma_update(None, "journal_mode", "WAL")Switches the database to Write-Ahead Logging, where readers and a writer can generally proceed concurrently instead of a writer exclusively locking the whole file.No direct C++ analogue; closest to choosing a database engine's concurrency mode at connect time.
conn.busy_timeout(Duration)Installs a busy handler so a connection that finds the database locked retries for up to the given duration instead of immediately returning SQLITE_BUSY.Similar to setting a retry/backoff policy on a resource lock rather than failing on first contention.
pragma_update(None, "foreign_keys", true)Turns on enforcement of REFERENCES constraints for this connection; SQLite ships with foreign-key enforcement off by default for backward compatibility, and the setting does not carry over between connections.No C++ analogue with a global default; closer to opting in to a validation mode that some database engines instead enable unconditionally.
⚠️
Connection is confined to one thread

rusqlite::Connection is Send but not Sync: it can be moved to another thread, but it cannot be shared by reference across threads at the same time, because the underlying SQLite handle is not safe for concurrent use without external synchronization. Pulsewatch gives each worker its own Connection (SQLite's WAL mode lets multiple connections to the same file coexist), rather than wrapping one connection in Arc<Mutex<Connection>> and serializing every query through it. Lesson 15 revisits this with a proper pool.

Part 2: versioned migrations with user_version

SQLite reserves an integer, PRAGMA user_version, for applications to track their own schema version inside the database file itself. Applying the DDL and bumping that version outside of an explicit transaction would let a mid-migration failure leave a database with the new tables but the old version number — this lesson wraps both in one conn.transaction() so the upgrade is all-or-nothing.

Excerpt from crates/pulsewatch-cli/src/store.rs (continues the same file as Part 1; the exercise gives the complete file):

const SCHEMA_VERSION: i64 = 1;

pub fn migrate(conn: &mut Connection) -> rusqlite::Result<()> {
    let current: i64 = conn.query_row("PRAGMA user_version", [], |row| row.get(0))?;

    if current < 1 {
        // Run the schema DDL and the user_version bump inside one explicit
        // transaction. user_version lives in the database file's own header
        // page, so writing it participates in the same commit as the CREATE
        // TABLE statements: either both land, or (on any error, or if this
        // function returns before tx.commit()) neither does. Without this,
        // a crash or error between creating the tables and bumping the
        // version would leave the file with tables already present but
        // user_version still 0, and the next run would fail re-creating them.
        let tx = conn.transaction()?;
        tx.execute_batch(
            "CREATE TABLE targets (
                 id   INTEGER PRIMARY KEY,
                 name TEXT NOT NULL UNIQUE,
                 host TEXT NOT NULL,
                 port INTEGER NOT NULL
             );
             CREATE TABLE probe_results (
                 id          INTEGER PRIMARY KEY,
                 target_id   INTEGER NOT NULL REFERENCES targets(id),
                 success     INTEGER NOT NULL,
                 latency_ms  INTEGER NOT NULL,
                 message     TEXT,
                 checked_at  TEXT NOT NULL
             );",
        )?;
        tx.pragma_update(None, "user_version", 1)?;
        tx.commit()?;
    }

    Ok(())
}
Rust syntaxMeaningC++ bridge
conn.query_row(sql, [], |row| ...)Runs a query expected to return exactly one row, invoking the closure once with that row to extract values.Similar to executing a prepared statement, stepping it once, and reading columns, but with a single call instead of prepare/step/finalize managed by hand.
conn.transaction()Begins an explicit transaction and returns a Transaction guard; every statement run through tx below is part of the same atomic unit of work.Comparable to an RAII transaction guard wrapping BEGIN/COMMIT/ROLLBACK around a multi-statement schema change.
tx.execute_batch(sql)Runs one or more semicolon-separated statements that return no rows, used here for DDL such as CREATE TABLE, inside the open transaction.Analogous to executing a multi-statement schema script through sqlite3_exec, but scoped inside a transaction instead of running each statement in its own implicit commit.
tx.pragma_update(None, "user_version", 1)Writes the new version into the same transaction as the DDL above; because user_version lives in the database file's header page, this write is committed or rolled back together with the table creation.No direct analogue: most engines keep schema-version metadata in an ordinary table, which is transactional by default, whereas here the version lives in file-level metadata that must be explicitly folded into the transaction to get the same guarantee.
tx.commit()Commits the DDL and the version bump together; if this line is never reached, dropping tx rolls both back.Same idea as an explicit commit() on a transaction RAII object guarding several related statements.
row.get(0)Reads column 0, converting the stored SQLite type into the target Rust type (i64 here) and returning a rusqlite::Result.Comparable to sqlite3_column_int64, but returning a checked Result instead of a raw value with a separate error check.
message TEXT (no NOT NULL)This column may hold SQL NULL; Part 3 maps that to Option<String> on the Rust side.Similar to a nullable column mapped to std::optional<std::string> rather than relying on a sentinel value such as an empty string.

Part 3: prepared statements, named parameters, and NULL as Option<T>

Excerpt from crates/pulsewatch-cli/src/store.rs (continues the same file as Parts 1 and 2; the exercise gives the complete file):

use rusqlite::{params, OptionalExtension};

pub fn insert_target(conn: &Connection, name: &str, host: &str, port: u16) -> rusqlite::Result<i64> {
    conn.execute(
        "INSERT INTO targets (name, host, port) VALUES (?1, ?2, ?3)",
        params![name, host, port],
    )?;
    Ok(conn.last_insert_rowid())
}

pub struct StoredResult {
    pub success: bool,
    pub latency_ms: i64,
    pub message: Option<String>,
    pub checked_at: String,
}

pub fn recent_results(conn: &Connection, target_name: &str, limit: i64) -> rusqlite::Result<Vec<StoredResult>> {
    let mut stmt = conn.prepare(
        "SELECT r.success, r.latency_ms, r.message, r.checked_at
         FROM probe_results r
         JOIN targets t ON t.id = r.target_id
         WHERE t.name = :name
         ORDER BY r.checked_at DESC
         LIMIT :limit",
    )?;

    let rows = stmt.query_map(
        rusqlite::named_params! { ":name": target_name, ":limit": limit },
        |row| {
            Ok(StoredResult {
                success: row.get::<_, i64>(0)? != 0,
                latency_ms: row.get(1)?,
                message: row.get(2)?,
                checked_at: row.get(3)?,
            })
        },
    )?;

    rows.collect()
}
Rust syntaxMeaningC++ bridge
params![name, host, port]Builds a parameter list bound by position (?1, ?2, ?3); each value is sent to SQLite separately from the SQL text.Comparable to binding values to ? placeholders in a prepared sqlite3_stmt rather than formatting them into the SQL string.
conn.last_insert_rowid()Returns the automatically assigned INTEGER PRIMARY KEY of the row just inserted on this connection.Similar to reading a database's identity/auto-increment value immediately after an insert on the same connection.
:name / :limit with named_params!Named placeholders bound by name instead of position, useful once a query has several parameters and positional order becomes error-prone.Comparable to named bind parameters supported by some prepared-statement APIs, versus purely positional ? placeholders.
message: Option<String> from row.get(2)rusqlite maps a NULL column value to None and a present value to Some(String) automatically when the target type is Option<String>.Equivalent in intent to mapping a nullable database column to std::optional<std::string> instead of a magic empty-string sentinel.
🛡️
SQL injection is a string-formatting bug, and parameters are the fix

Building the query above as format!("... WHERE t.name = '{target_name}' ...") would let a target name containing a single quote change the query's meaning entirely — classic SQL injection. Binding target_name through params! or named_params! sends it to SQLite as data, never as SQL text, which closes that class of bug regardless of what characters the value contains.

Part 4: transactions batch writes and roll back correctly on error

Excerpt from crates/pulsewatch-cli/src/store.rs (continues the same file as Parts 1 through 3; the exercise gives the complete file):

pub fn record_batch(
    conn: &mut Connection,
    target_id: i64,
    outcomes: &[pulsewatch_core::ProbeOutcome],
) -> rusqlite::Result<()> {
    let tx = conn.transaction()?;
    {
        let mut stmt = tx.prepare(
            "INSERT INTO probe_results (target_id, success, latency_ms, message, checked_at)
             VALUES (?1, ?2, ?3, ?4, datetime('now'))",
        )?;
        for outcome in outcomes {
            stmt.execute(params![
                target_id,
                outcome.success as i64,
                outcome.latency_ms as i64,
                outcome.message,
            ])?;
        }
    }
    tx.commit()
}
Rust syntaxMeaningC++ bridge
conn.transaction()Begins a transaction and returns a Transaction guard borrowing the connection for its lifetime.Comparable to an RAII transaction guard wrapping BEGIN/COMMIT/ROLLBACK.
tx.commit()Explicitly commits; consumes the guard so it cannot be committed twice.Same idea as an explicit commit() call on a transaction RAII object.
No explicit rollback() call on the early-return ? pathsIf ? returns early anywhere before tx.commit() runs, tx is dropped without being committed, and its Drop implementation issues ROLLBACK automatically.Directly analogous to RAII rollback-on-scope-exit: the transaction is undone unless the commit path is reached, with no explicit catch/rollback needed.

Every insert in the loop shares one transaction, so SQLite fsyncs once at commit instead of once per row — the same batching benefit any transactional database gives a caller that groups related writes.

Knowledge check

1. Why does migrate read PRAGMA user_version before creating any tables, and why does it wrap the CREATE TABLE statements and the version bump in one conn.transaction()?

Answer: user_version is an integer SQLite stores in the database file for the application's own use; reading it first lets migrate apply only the schema changes a given file has not already received, so running it again against an already-migrated file is a no-op. Wrapping the DDL and the PRAGMA user_version update in one transaction matters because user_version lives in the same file header page that participates in SQLite's normal commit/rollback: if a failure happened between creating the tables and bumping the version with no transaction, the file could be left with the new tables but the old version number, and the next run would fail trying to re-create them.

2. What happens to a NULL value stored in the message column when it is read into a Rust Option<String> field?

Answer: rusqlite maps SQL NULL to None and any present text value to Some(String) when the target field's type is Option<String>, so the absence of a message is represented directly rather than through an empty-string sentinel.

3. Why is binding target_name through named_params! safer than formatting it directly into the SQL string?

Answer: A bound parameter is sent to SQLite as a value, never interpreted as SQL syntax, so characters like a single quote in the value cannot change the query's structure. Formatting the value into the SQL string directly opens a SQL injection vulnerability where an attacker-controlled value can alter or extend the query.

4. If stmt.execute(...) inside record_batch returns an error partway through the loop, what happens to the rows already inserted in that same call?

Answer: The ? operator returns early, so tx.commit() is never reached and the Transaction guard is dropped instead. Its Drop implementation issues ROLLBACK, undoing every insert performed earlier in that same transaction, so the batch is all-or-nothing.

Recap and decision rules

Opening a database used by more than one connection?  Enable WAL, set a busy_timeout
Want REFERENCES constraints enforced?                   pragma_update(None, "foreign_keys", true) on every connection
Schema needs to evolve over time?                       Track it with PRAGMA user_version
Migration must not land half-applied?                   Run the DDL and the user_version bump in one conn.transaction()
Passing an external value into SQL?                     Bind it with params!/named_params!, never format it in
Column can be absent?                                   Model it as Option<T> on the Rust side
Several related writes must all succeed or none do?     Wrap them in one conn.transaction()
Need the transaction undone on any early error?          Let ? drop the guard; Drop runs ROLLBACK
Sharing one Connection across threads?                    Don't: Connection is Send, not Sync
