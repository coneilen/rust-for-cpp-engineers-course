Production Service with SQLx

Migrate Pulsewatch's persistence from a blocking driver to an async SQLx pool with compile-time checked queries, migrations, transactions, bounded concurrency, environment configuration, and graceful shutdown.

By the end: you can open an async SQLx pool, explain what compile-time checked queries require at build time (and the offline-metadata caveat), run embedded migrations, wrap related writes in a transaction, bound concurrent database access, load configuration from the environment, and shut the service down gracefully.

Part 1: why an async pool replaces a blocking connection

Lesson 14 gave pulsewatch-cli a local store for targets and probe_results through rusqlite, a synchronous driver: every worker opened its own Connection, and any query that needed to run alongside async code elsewhere in Pulsewatch had to hop onto a blocking thread with tokio::task::spawn_blocking to avoid stalling a runtime. This lesson keeps that exact schema and the same targets/probe_results history, but moves the store itself to SQLx, an async, compile-time-checked SQL toolkit, and adds it to pulsewatch-service, the package this lesson's Follow-along setup just created by migrating Lesson 13's router and binary out of pulsewatch-cli, so its Axum routes can serve target history over HTTP.

SQLite has no asynchronous I/O of its own — every read or write is still a blocking call into the SQLite C library. SQLx's SQLite driver does not avoid that; instead, each SqliteConnection it opens runs on its own dedicated background thread, and your async code communicates with that thread over a channel, awaiting the reply instead of blocking the calling task. That removes the need to call spawn_blocking by hand at every query site, but it is not "non-blocking SQLite I/O": the blocking work still happens, just confined to a worker thread SQLx manages for you.

SQLx's other defining feature is compile-time checked queries. Macros such as sqlx::query! and sqlx::query_as! send your SQL text to a real database (or a cached schema snapshot) while the crate compiles, and fail the build if a column name, type, or argument count does not match the schema.

crates/pulsewatch-service/Cargo.toml — append to the existing [dependencies] table
sqlx = { version = "0.8", features = ["runtime-tokio", "sqlite", "macros", "migrate"] }
crates/pulsewatch-service/src/db.rs — create
use sqlx::sqlite::SqlitePoolOptions;
use sqlx::SqlitePool;
use std::time::Duration;

pub async fn connect(database_url: &str) -> Result<SqlitePool, sqlx::Error> {
    let pool = SqlitePoolOptions::new()
        .max_connections(5)
        .acquire_timeout(Duration::from_secs(5))
        .connect(database_url)
        .await?;
    sqlx::migrate!("./migrations").run(&pool).await?;
    Ok(pool)
}
crates/pulsewatch-service/src/main.rs — append (one line, near the top of the file, above every function that calls db::connect or db::recent_results)
mod db;

This one line is what makes db.rs part of the binary at all: without it, db::connect and db::recent_results later in this lesson would not resolve, because a file sitting next to main.rs is not automatically compiled in — it has to be declared as a module.

⚠️
The offline-metadata caveat

query! and query_as! need either a reachable database at DATABASE_URL during cargo build, or a checked-in .sqlx metadata cache produced by cargo sqlx prepare and consumed when SQLX_OFFLINE=true. A CI job that has neither will fail to build; a stale .sqlx cache that nobody regenerated after a migration can pass a build against a schema the database no longer has. Treat .sqlx as generated, reviewed output, not a file you hand-edit.

Keep two differently-scoped environment variables straight here. DATABASE_URL above is read only by the sqlx::query!/query_as! macros and by cargo sqlx prepare, at cargo build time, purely to check queries against a schema; it does not need to point at the database the compiled binary will actually use, and in CI it is often a disposable, empty database used for nothing but compile-time checking. The service's own runtime configuration, read once at startup, is a separate variable, PULSEWATCH_DATABASE_URL, introduced in Part 3. In development the two commonly point at the same file; conflating them in CI or production is a common source of "it built fine but connected to the wrong database" surprises.

Part 2: a schema-preserving migration, and transactions

A migration is a versioned, forward-moving SQL file; SQLx embeds them in the binary and applies any that have not yet run. Migration 0001 recreates exactly the targets and probe_results tables Lesson 14 created by hand through PRAGMA user_version = 1, so a database file that already has them, and every row of target and probe history in them, is left untouched. Create the migrations directory first, from the workspace root:

mkdir -p crates/pulsewatch-service/migrations
crates/pulsewatch-service/migrations/0001_targets_probe_results.sql — create
-- migrations/0001_targets_probe_results.sql
CREATE TABLE IF NOT EXISTS targets (
    id   INTEGER PRIMARY KEY,
    name TEXT NOT NULL UNIQUE,
    host TEXT NOT NULL,
    port INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS probe_results (
    id          INTEGER PRIMARY KEY,
    target_id   INTEGER NOT NULL REFERENCES targets(id),
    success     INTEGER NOT NULL,
    latency_ms  INTEGER NOT NULL,
    message     TEXT,
    checked_at  TEXT NOT NULL
);
🧭
Converting an existing database to SQLx's migration tracking

A pulsewatch.db file Lesson 14 already migrated has these exact tables, but SQLx does not know that: it tracks progress in its own _sqlx_migrations table, entirely separate from SQLite's PRAGMA user_version. IF NOT EXISTS is what makes this safe — the statements become no-ops against an already-populated file, so sqlx::migrate! can run against it for the first time without touching a single existing row, and only then does it record migration 0001 as applied. A migration that needed to reshape existing data, rather than merely assert the same shape already exists, would instead need an explicit ALTER TABLE and backfill step written into that same migration file, run once and never edited after it has shipped.

A batch of related writes should either all land or none do. pool.begin() returns a Transaction that rolls back automatically if it is dropped without an explicit commit:

crates/pulsewatch-service/src/db.rs — append (continues after the connect function above)
#[derive(Debug, serde::Serialize, sqlx::FromRow)]
pub struct StoredResult {
    pub success: bool,
    pub latency_ms: i64,
    pub message: Option<String>,
    pub checked_at: String,
}

pub async fn record_batch(
    pool: &SqlitePool,
    target_id: i64,
    outcomes: &[pulsewatch_core::ProbeOutcome],
) -> Result<(), sqlx::Error> {
    let mut tx = pool.begin().await?;
    for outcome in outcomes {
        let latency_ms = outcome.latency_ms as i64;
        sqlx::query!(
            "INSERT INTO probe_results (target_id, success, latency_ms, message, checked_at)
             VALUES (?, ?, ?, ?, datetime('now'))",
            target_id,
            outcome.success,
            latency_ms,
            outcome.message,
        )
        .execute(&mut *tx)
        .await?;
    }
    tx.commit().await?;
    Ok(())
}

pub async fn recent_results(
    pool: &SqlitePool,
    target_name: &str,
    limit: i64,
) -> Result<Vec<StoredResult>, sqlx::Error> {
    sqlx::query_as!(
        StoredResult,
        r#"SELECT r.success as "success: bool", r.latency_ms, r.message, r.checked_at
           FROM probe_results r
           JOIN targets t ON t.id = r.target_id
           WHERE t.name = ?
           ORDER BY r.checked_at DESC
           LIMIT ?"#,
        target_name,
        limit
    )
    .fetch_all(pool)
    .await
}

If any insert in the loop fails, ? returns early, tx is dropped without a commit, and SQLite rolls the whole batch back. No target's history is left half-recorded. recent_results reuses Lesson 14's own query almost verbatim, joined against targets by name; the one addition, as "success: bool", overrides SQLx's compile-time type inference for a column declared INTEGER so it decodes as bool without changing the schema on disk.

Part 3: bounded concurrency, configuration, and shutdown

An async pool lets many requests reach the database concurrently, but a single SQLite file still serializes writes and has a connection ceiling. A Semaphore caps how many requests may be mid-query at once, independent of how many HTTP requests Tokio is otherwise juggling. AppState keeps Lesson 13's http_client field and adds the pool and semaphore alongside it:

crates/pulsewatch-service/src/main.rs — replace the existing struct AppState block from Lesson 13
#[derive(Clone)]
pub struct AppState {
    pub http_client: reqwest::Client,
    pub pool: SqlitePool,
    pub db_reads: Arc<Semaphore>,
}

Configuration and secrets come from the environment, never from source — but keep the two DATABASE_URL-shaped variables from Part 1 separate in your head. DATABASE_URL is a build-time-only concern for the sqlx macros; PULSEWATCH_DATABASE_URL below is this service's own runtime configuration, read once at startup and used to decide which database file the running process actually opens. This replaces Lesson 13's --addr CLI flag with an environment variable read at the same startup point, so the bind address and the database URL are configured the same way:

impl AppConfig {

Lesson 13 already stops pulsewatch-service gracefully: serve calls axum::serve(listener, router).with_graceful_shutdown(shutdown_signal()), which stops accepting new connections on Ctrl+C but lets any in-flight request finish first. No new shutdown code is needed here — target_history is an ordinary handler, so a request already in that handler when Ctrl+C is pressed keeps its Semaphore permit and finishes its query before the process exits, the same as any other in-flight request.

The #[tokio::main] async fn main() moved in from Lesson 13's binary parsed --addr from std::env::args() and built an AppState with only an HTTP client. Replace it so it loads AppConfig, opens the pool through db::connect, and builds the three-field AppState defined earlier in this same file before serving:

crates/pulsewatch-service/src/main.rs — replace the existing #[tokio::main] async fn main() moved from Lesson 13
#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let config = AppConfig::from_env()?;
    let pool = db::connect(&config.database_url).await?;
    let state = Arc::new(AppState {
        http_client: build_http_client()?,
        pool,
        db_reads: Arc::new(Semaphore::new(config.max_db_reads)),
    });
    let router = build_router_with_middleware(state);
    serve(router, config.bind_addr).await?;
    Ok(())
}

AppConfig::from_env()? replaces the old --addr parsing entirely: any missing or malformed environment variable now fails startup immediately with a message from .context(...), before a socket is ever bound. build_http_client()?, db::connect(...).await?, and serve(...).await? each propagate their own error type through anyhow's blanket conversion, so main needs no manual match on three different error enums.

pub fn build_http_client() -> reqwest::Result<reqwest::Client> {
    reqwest::Client::builder()
        .connect_timeout(Duration::from_secs(3))
        .timeout(Duration::from_secs(5))
        .pool_max_idle_per_host(8)
        .build()
}

pub async fn probe_http(
    client: &reqwest::Client,
    url: &str,
) -> Result<pulsewatch_core::ProbeOutcome, reqwest::Error> {
    const MAX_BODY_BYTES: usize = 64 * 1024;
    let started = tokio::time::Instant::now();

    let mut response = client.get(url).send().await?;
    let status = response.status();

    if let Some(len) = response.content_length() {
        if len as usize > MAX_BODY_BYTES {
            return Ok(pulsewatch_core::ProbeOutcome {
                target: url.to_string(),
                success: false,
                latency_ms: started.elapsed().as_millis(),
                message: format!("body too large: {len} declared bytes"),
            });
        }
    }

    let mut body = Vec::new();
    while let Some(chunk) = response.chunk().await? {
        if body.len() + chunk.len() > MAX_BODY_BYTES {
            return Ok(pulsewatch_core::ProbeOutcome {
                target: url.to_string(),
                success: false,
                latency_ms: started.elapsed().as_millis(),
                message: format!("body exceeded {MAX_BODY_BYTES} bytes while streaming"),
            });
        }
        body.extend_from_slice(&chunk);
    }

    let text = String::from_utf8_lossy(&body);
    Ok(pulsewatch_core::ProbeOutcome {
        target: url.to_string(),
        success: status.is_success(),
        latency_ms: started.elapsed().as_millis(),
        message: format!("{status}: {text}"),
    })
}

pub fn build_router_with_middleware(state: Arc<AppState>) -> Router {
    build_router(state)
        .layer(RequestBodyLimitLayer::new(64 * 1024))
        .layer(TimeoutLayer::new(Duration::from_secs(10)))
}

pub async fn serve(router: Router, addr: SocketAddr) -> std::io::Result<()> {
    let listener = tokio::net::TcpListener::bind(addr).await?;
    axum::serve(listener, router)
        .with_graceful_shutdown(shutdown_signal())
        .await
}

async fn shutdown_signal() {
    tokio::signal::ctrl_c()
        .await
        .expect("failed to install Ctrl+C handler");
}

    fn from_env() -> anyhow::Result<Self> {
        Ok(Self {
            database_url: std::env::var("PULSEWATCH_DATABASE_URL")
                .context("PULSEWATCH_DATABASE_URL must be set")?,
            bind_addr: std::env::var("PULSEWATCH_BIND_ADDR")
                .unwrap_or_else(|_| "127.0.0.1:8080".to_string())
                .parse()
                .context("PULSEWATCH_BIND_ADDR must be host:port")?,
            max_db_reads: 16,
        })
    }
}

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let config = AppConfig::from_env()?;
    let pool = db::connect(&config.database_url).await?;
    let state = Arc::new(AppState {
        http_client: build_http_client()?,
        pool,
        db_reads: Arc::new(Semaphore::new(config.max_db_reads)),
    });
    let router = build_router_with_middleware(state);
    serve(router, config.bind_addr).await?;
    Ok(())
}

Worked Pulsewatch increment

Together these pieces replace Lesson 14's blocking store with an async one, while keeping the exact same targets/probe_results schema and history: pulsewatch-service now opens one SqlitePool at startup, runs the schema-preserving migration, serves target history through a semaphore-bounded handler alongside its existing Lesson 13 routes, writes probe result batches inside transactions, loads its configuration from PULSEWATCH_DATABASE_URL at runtime (kept separate from the build-time DATABASE_URL the query macros use), and keeps Lesson 13's graceful shutdown, which already drains this new handler along with every other in-flight request.

🧭
Stability and production boundary

This lesson makes persistence async and adds compile-time checked queries, migrations, transactions, bounded concurrency, environment-based configuration, and graceful shutdown — it does not make the service production-ready by itself. There is still no connection-pool observability, no retry/backoff policy for transient database errors, no secrets manager (only environment variables), and no coordination across multiple replicas during shutdown. Each is a real, separate concern.

Knowledge check

1. What must be true at cargo build time for sqlx::query! to compile, and what happens in CI if neither option is available?

Answer: Either a live database reachable at DATABASE_URL, or a checked-in .sqlx offline metadata cache consumed with SQLX_OFFLINE=true. Without either, the build fails at the macro. This DATABASE_URL is a build-time-only concern, unrelated to the runtime PULSEWATCH_DATABASE_URL the running service reads at startup.

2. Why wrap the batch insert in pool.begin() instead of issuing each insert directly against the pool?

Answer: A transaction makes the batch atomic: dropping it without commit() rolls back every insert in it, so a mid-batch failure never leaves a partial write.

3. What does bounding reads with a Semaphore protect against that an unbounded fan-out of concurrent queries would not?

Answer: It caps how many requests can be mid-query against the single SQLite file at once, preventing connection-pool exhaustion and excessive write/read contention under bursty traffic.

4. Why does AppConfig::from_env read PULSEWATCH_DATABASE_URL from the environment instead of hardcoding it?

Answer: Credentials and endpoints must not be compiled into the binary or committed to source. PULSEWATCH_DATABASE_URL is also a separate variable from the build-time DATABASE_URL the sqlx macros use, so the database a developer's machine builds against and the database the deployed service actually connects to can safely be two different things.

5. Why does recent_results need r.success as "success: bool" instead of just declaring the StoredResult.success field as bool?

Answer: SQLx infers each selected column's Rust type from its declared SQL type; probe_results.success is declared INTEGER, not BOOLEAN, so without the override the macro would check the column as an integer type. The as "success: bool" annotation tells the compile-time checker to decode that column as bool without changing the on-disk schema.

6. A pulsewatch.db file already migrated by Lesson 14's rusqlite-based PRAGMA user_version = 1 step is opened by sqlx::migrate! for the first time. Why doesn't migration 0001 destroy its existing targets and probe_results rows?

Answer: CREATE TABLE IF NOT EXISTS is a no-op when the tables are already present, so the migration succeeds without touching any existing table or row. SQLx tracks which migrations have run in its own _sqlx_migrations table, separate from SQLite's user_version, and only records 0001 as applied after this first successful run, leaving all prior target and probe history intact.

Recap and decision rules

Blocking driver stalling the async runtime?   Move to an async pool (SqlitePool)
SQLite has no async I/O of its own?            SQLx still blocks, just on its own worker thread per connection, via a channel
Want the compiler to catch a bad column/type?  sqlx::query!/query_as! against a live DB or .sqlx cache
Schema says INTEGER but you want bool?         Override with as "col: bool" in the query text
Adopting SQLx migrations on an existing schema? Make migration 0001 idempotent (IF NOT EXISTS); existing rows survive untouched
Several writes must succeed together?          pool.begin() ... tx.commit()
Many requests, one contended database file?    Bound concurrent access with a Semaphore
Build-time vs runtime database URL?            DATABASE_URL is for sqlx macros only; PULSEWATCH_DATABASE_URL is the running service's config
Need a clean exit under load?                   axum::serve(...).with_graceful_shutdown(signal)
