Values, Variables, Scalar Types, Storage, and Constants

Bind values with let, choose scalar types on purpose, understand what Rust actually promises about stack and heap storage, and add compile-time constants to rust-greeter — without introducing a struct yet.

Part 1: let, immutability, mut, and shadowing

A C++ local is mutable unless you write const. Rust inverts the default: let bindings are immutable unless you write mut.

Rust: rejected without mut
let count = 1;
count = 2; // error[E0384]: cannot assign
           // twice to immutable variable
Rust: works with mut
let mut count = 1;
count = 2; // fine: `count` opted into mutation

Shadowing is not mutation. A second let with the same name introduces a brand-new binding — it can even change type — and the old binding is simply no longer reachable by that name. This differs from re-declaring a C++ variable in an inner scope, because shadowing can happen in the very same scope:

let count = "3";          // count: &str
let count: u8 = count.parse().unwrap(); // count: u8 — a new binding, same name
let count = count * 2;    // count: u8 — another new binding
C++ instinctRust reality
const auto x = ...; is the careful defaultlet x = ...; is the default; mut is the deliberate opt-in
Re-declaring x in the same scope is an errorShadowing lets a new let x reuse the name and even change the type
Mutating a variable keeps its address and typeShadowing may produce a differently typed value with no relation to the old storage

Part 2: scalar types, literals, and checked conversions

Rust's scalar primitives are explicit about width and signedness. There is no implicit widening or narrowing between numeric types the way C++ allows between int, long, and double.

CategoryRust typesC++ bridge
Signed integersi8 i16 i32 i64 i128int8_t … int64_t, plus a 128-bit type C++ lacks natively
Unsigned integersu8 u16 u32 u64 u128uint8_t … uint64_t, plus 128-bit
Pointer-sizedisize / usizeptrdiff_t / size_t — sized to address the machine, used for indices and lengths
Floating pointf32 / f64float / double
Booleanboolbool; exactly one byte, only true/false
CharactercharNo exact match: always a 4-byte Unicode scalar value, not one byte and not always one printed "character" (a display grapheme can be several chars)

Literals can carry an explicit suffix, or let the compiler infer from context: let repeats = 3u8; and let repeats: u8 = 3; declare the same value. Underscores are just readability separators: 1_000_000i64.

An integer-to-integer cast with as is a blunt tool: it always produces a value, silently truncating and wrapping (two's-complement, modulo the target width) when the target type cannot represent the input. A float-to-integer as cast behaves differently — since Rust 1.45 it saturates instead of wrapping: a value too large becomes the target type's maximum, a value too negative becomes its minimum, and NaN becomes 0. TryFrom (used through u8::try_from) checks an integer-to-integer conversion and returns a Result instead of guessing; the standard library does not provide a TryFrom for float-to-integer conversions, so a checked float-to-integer conversion still needs a manual range/NaN check (or a crate such as num-traits). File: src/main.rs — add below fn greeting:

fn describe_cast(value: i32) -> String {
    let truncated = value as u8;
    match u8::try_from(value) {
        Ok(exact) => format!("{value} as u8 = {truncated}; try_from = {exact}"),
        Err(_) => format!("{value} as u8 = {truncated} (truncated); try_from does not fit"),
    }
}
CallResult
describe_cast(200)"200 as u8 = 200; try_from = 200" — 200 fits in a u8, so both paths agree.
describe_cast(1000)"1000 as u8 = 232 (truncated); try_from does not fit" — 1000 as u8 silently wraps modulo 256 because this is an integer-to-integer cast; u8::try_from(1000) reports Err instead of guessing. (A float-to-integer as cast, e.g. 1000.0f64 as u8, would instead saturate to 255 — it does not wrap.)
🛑
as never panics, and that is the danger

A C++ narrowing conversion is often a compiler warning you can miss. Rust's as is intentionally silent about range for both cases — wrapping on integer-to-integer casts, saturating on float-to-integer casts — which is why any cast whose input range you cannot fully guarantee should prefer a checked path (TryFrom/TryInto for integer-to-integer, or an explicit range/NaN check for float-to-integer) and handle the failure case, rather than reaching for as.

Part 3: tuples, arrays, Copy vs. move, and "POD"

A tuple groups a fixed, possibly heterogeneous set of values by position; an array holds a fixed number of same-typed values. Both live inline, with no heap allocation of their own:

let point: (i32, i32) = (3, 4);
let first = point.0;              // access by position
let scores: [u32; 3] = [10, 20, 30];
let second_score = scores[1];      // access by index, bounds-checked

Rust has no official "plain old data" category the way C++ does. Instead, the compiler tracks a specific trait, Copy: a type is Copy only if copying its bytes is always correct and cheap, and only if every field is also Copy. All scalar primitives are Copy; a tuple or array of Copy elements is Copy too. A type that owns a heap allocation, such as String, is never Copy — assigning it moves it instead of duplicating the buffer, and the source binding stops being usable.

C++ "POD" instinctRust reality
"POD" implies bitwise copy is safeRust calls that property Copy; it is a trait the compiler derives or verifies, not a language keyword
"POD" often also implies a stable, C-compatible byte layoutCopy says nothing about layout. Rust's default struct layout may reorder fields; stable byte layout for FFI needs an explicit #[repr(C)] (Lesson 19), which is a separate, stronger guarantee
Assigning a struct always copies itAssigning a non-Copy struct moves it: the source binding is invalidated by the compiler, not merely discouraged by convention

A move is a beginner-visible example of ownership, which Lesson 5 covers in depth. For now: passing or assigning a String transfers ownership, while passing or assigning a u8 or a tuple of u8s simply copies cheap bytes and both bindings stay valid.

Part 4: what "storage" means in Rust

C++ trains you to reason about stack versus heap by variable declaration. Rust asks a related but different question: who owns this value, and does that owner's type own a heap allocation?

Value or typeWhat actually happens
A local let x = 5u8;Conceptually a local variable. The compiler is free to keep it in a register or optimize it away entirely — "stack vs. heap" for locals is an implementation detail, not a language guarantee.
String, Vec<T>Each is a three-word handle (pointer, length, capacity) that may own a heap allocation once it needs one. String::new()/Vec::new() start at capacity zero and allocate nothing until data is pushed in; once they do allocate, the bytes live on the heap and are freed when the owning handle is dropped.
Box<T>A single pointer-like owning handle for one heap-allocated T — unlike a plain reference, dropping the Box frees the value. A Box of a zero-sized type is the exception: there are no bytes to store, so it requires no actual heap allocation.
&strA borrowed view into UTF-8 bytes owned elsewhere — a pointer plus a length, not an owner. It never allocates or frees anything itself.
A string literal, e.g. "casual"Baked into the compiled binary and valid for the entire program. Its type is &'static str: a borrowed view whose data needs no owner because the program itself outlives it.

This is why fn greeting(name: &str) -> String from Lesson 1 reads correctly once you separate "local variable" from "heap owner": name is a local binding holding a borrowed view, regardless of whether the string it views is a heap-owned String or a 'static literal; the return type String is a new, owned heap allocation the caller now owns.

Part 5: const, static, and const fn

const and static both require a value known at compile time, but they are not interchangeable:

DeclarationMeaning
const NAME: T = value;Inlined at every use site, like a C++ constexpr. It has no fixed address and cannot be mutated.
static NAME: T = value;One fixed memory location for the whole program, closer to a C++ file-scope static const. Still immutable by default.
const fn name(...) -> TAn ordinary function that the compiler can also evaluate at compile time when its inputs are constant — used below to compute CLAMPED_DEFAULT before the program even starts.

File: src/main.rs — add above fn greeting (order does not matter for items, but keeping related pieces together helps readability):

const MAX_REPEATS: u8 = 9;
static APP_NAME: &str = "rust-greeter";

const fn clamp_repeats(requested: u8) -> u8 {
    if requested > MAX_REPEATS {
        MAX_REPEATS
    } else {
        requested
    }
}

const CLAMPED_DEFAULT: u8 = clamp_repeats(20);

CLAMPED_DEFAULT is computed by the compiler, not at runtime: clamp_repeats(20) is evaluated during compilation because clamp_repeats is a const fn and 20 is a literal, so the binary already contains the answer, 9.

🛑
static mut is a real warning sign, not a stylistic one

Rust allows static mut COUNTER: u32 = 0;, but every read or write requires an unsafe block, and even that is not automatically sound. A shared reference into a mutable static is undefined behavior if the static is ever mutated while that reference is alive, so recent Rust editions reject the most common naive pattern outright:

Illustrative excerpt — not added to rust-greeter. This shows the exact compiler rejection so you recognize it if you see it, and the safe alternative you should reach for instead:

Rejected: shared reference to a mutable static
static mut COUNTER: u32 = 0;

fn main() {
    unsafe {
        COUNTER += 1;
        println!("{}", COUNTER); // error: creating a shared
    }                            // reference to mutable static
}
Safe: an atomic instead of static mut
use std::sync::atomic::{AtomicU32, Ordering};

static COUNTER: AtomicU32 = AtomicU32::new(0);

fn main() {
    COUNTER.fetch_add(1, Ordering::Relaxed);
    println!("{}", COUNTER.load(Ordering::Relaxed));
}

The right-hand version compiles and prints 1 today. Lesson 10 covers Ordering and atomics properly; for now, the rule is simple: prefer an owned local, or a safe wrapper like an atomic, over static mut.

Part 6: grow rust-greeter with a GreeterConfig-style grouping

Lesson 3 introduces a real GreeterConfig struct. Before structs exist in this course, a plain tuple can still group related values — which is itself a preview of what a struct buys you (names instead of positions). File: src/main.rs — replace the existing fn main from Lesson 1 with:

fn main() {
    let args = Args::parse();

    // Shadowing: each `let count` introduces a new binding; this is not mutation.
    let count = args.count;
    let count = clamp_repeats(count);

    // A GreeterConfig-style grouping, expressed as a tuple before Lesson 3 introduces a struct.
    let greeter_tuple: (String, bool, &str) =
        (args.name.clone(), args.name.contains(' '), "casual");
    let (name, is_team, style) = &greeter_tuple;

    println!("{APP_NAME} greeter tuple -> name={name}, is_team={is_team}, style={style}");
    println!(
        "cast demo: {}; compile-time clamped default: {CLAMPED_DEFAULT}",
        describe_cast(1000)
    );

    let mut greeted = 0u32;
    for _ in 0..count {
        println!("{}", greeting(name));
        greeted += 1;
    }
    println!("greeted {greeted} time(s)");
}
Rust syntaxMeaning
args.name.clone()An explicit, visible copy of the heap buffer. Required because String is not Copy — args.name is still needed later for .contains(' '), so it must not be moved out.
args.name.contains(' ')A borrowing method call on &str/String that returns bool — a Copy type, so using it later is never a move.
(String, bool, &str)A 3-element tuple type. Unlike a struct, its fields are accessed by position (.0, .1, .2) rather than by name.
let (name, is_team, style) = &greeter_tuple;Destructures a borrow of the tuple into three named bindings in one step, instead of three separate .0/.1/.2 accesses.
let mut greeted = 0u32;An explicit, deliberately mutable local counter — the only mutable binding in this file so far.

Knowledge check

1. Why does the second let count = clamp_repeats(count); not need mut?

Answer: It is shadowing, not mutation. Each let introduces a distinct new binding named count; the old one is no longer reachable by that name, so no in-place mutation occurs.

2. Why does describe_cast(1000) report a truncated value from as but an error from try_from?

Answer: as always produces a u8 by wrapping modulo 256 and never fails, silently losing information. u8::try_from checks the range first and returns Err when the value does not fit, so callers must handle the failure explicitly.

3. Is a String ever Copy? What happens when you assign one to a new binding?

Answer: No. String owns a heap allocation, so it can never be Copy. Assigning it moves ownership to the new binding, and the old binding can no longer be used — which is why the exercise calls args.name.clone() before also calling args.name.contains(' ').

4. Does Rust guarantee that a plain local let x = 5u8; lives on the stack?

Answer: No. That is an implementation detail the compiler may optimize freely, including keeping it in a register. Rust's real storage guarantees are about ownership: heap-owning types like String free their allocation when the owning binding is dropped, and borrowed views like &str can never outlive the data they view.

Recap and decision rules

Value should never change here?      Use `let` (the default)
Value must be reassigned in place?   Use `let mut`
Want a new binding, maybe new type?  Shadow with another `let`
Range of a numeric input is proven?  `as` is acceptable
Range of a numeric input is not?     Prefer `TryFrom`/`TryInto` and handle `Err`
Known at compile time, no address?   `const`
Known at compile time, one address?  `static` (never `static mut`; prefer an atomic)
Need to read text without owning it? `&str`
Need to own and possibly grow text?  `String`

You did not just memorize syntax: you separated "is this a new binding?" from "did I mutate a value?", separated "will this compile-time value have an address?", and separated "who owns this data?" from "where might the compiler happen to put it?".
