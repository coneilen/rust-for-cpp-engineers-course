Lesson 21 · 30 minutes

Kotlin & Java Bindings for Mobile

Give the Pulsewatch Android app its own on-device alert-scoring API: JNI fundamentals, the jni crate for hand-written glue, and a product-ready UniFFI Kotlin binding.

By the end: You can explain JNIEnv, local versus global references, and thread rules; call Rust from Java/Kotlin through the jni crate; generate a product-facing Kotlin API with UniFFI; and package the native library correctly for Android's per-ABI loadLibrary model.

Part 1: two ladder rungs for one goal

The Pulsewatch Android app wants offline alert triage — scoring recent samples without a network round trip — using the same pulsewatch-scoring Rust core built in Lessons 19 and 20. Kotlin compiles to the same JVM/ART bytecode as Java and calls native code through the identical Java Native Interface, so everything here applies to both languages. There are two ladder rungs: understand raw JNI first, because it explains what is really happening at the boundary, then generate the actual product API with UniFFI rather than hand-writing it.

Part 2: JNI fundamentals

JNI conceptWhat it meansC++ bridge
JNIEnv*A per-thread interface pointer into the JVM, valid only on the thread that received it.No direct C++ equivalent — closest to a thread-local capability object you must never share across threads.
Local referenceValid only for the duration of one native method call; the JVM manages a bounded table of them per call.Loosely like a scope-limited handle the runtime frees for you, not RAII you control.
Global referenceSurvives across calls and threads once created with NewGlobalRef, but must be explicitly released with DeleteGlobalRef or it leaks.Closest to a manually paired new/delete — no destructor frees it for you.
Strings and arraysjstring/array types require Get*/Release* pairs that copy or pin data; there is no direct pointer into Kotlin's managed string.Comparable to copying out of an opaque handle rather than borrowing through a reference.
ExceptionsJNI has no automatic propagation; a pending exception must be checked after any JNI call that can throw, and no further JNI calls are safe until it is cleared or handled.Unlike C++ exceptions, nothing unwinds the native stack for you — you poll for the pending state explicitly.
🧵
Threads need to attach before they can use JNIEnv

If Rust spawns its own OS thread that later needs to call back into the JVM, it must call AttachCurrentThread first and DetachCurrentThread before the thread exits. Only attach threads that genuinely need JVM access — attach/detach carries real overhead.

The JNI glue must reuse Lesson 19's stateful AlertScorer, not recompute a stateless score — a per-shard sliding window only works if the same scorer instance persists across calls. Rather than boxing a raw pointer into the jlong handle (Lesson 19's PwScorer pattern), the adapter below keeps every live scorer in a single mutex-guarded registry keyed by a monotonically generated ID. A raw boxed pointer would let one thread call nativeFree while another concurrently calls nativeScore on the same handle — a use-after-free. Looking the handle up in a locked map instead makes concurrent calls serialize, and a handle removed by nativeFree simply stops resolving, so a stale handle reaching nativeScore gets a clean exception instead of touching freed memory. File: path/to/pulsewatch/crates/pulsewatch-scoring/src/jni_bridge.rs (new file, complete):

// crates/pulsewatch-scoring/src/jni_bridge.rs
use jni::JNIEnv;
use jni::objects::{JClass, JString};
use jni::sys::{jdouble, jfloat, jlong};
use std::collections::HashMap;
use std::sync::atomic::{AtomicI64, Ordering};
use std::sync::{Mutex, OnceLock};
use std::time::Duration;
use crate::{AlertScorer, Sample, ScoringError};

/// Every live scorer lives here, keyed by a monotonically generated handle.
/// One process-wide mutex means nativeScore/nativeFree calls serialize --
/// exactly the exclusivity AlertScorer::score's `&mut self` already
/// requires -- and removing an entry from the map (nativeFree) is enough
/// to make a stale handle fail cleanly instead of dereferencing freed
/// memory, the way a raw `Box::into_raw`/`Box::from_raw` handle would.
static SCORERS: OnceLock<Mutex<HashMap<jlong, AlertScorer>>> = OnceLock::new();
static NEXT_HANDLE: AtomicI64 = AtomicI64::new(1);

fn registry() -> &'static Mutex<HashMap<jlong, AlertScorer>> {
    SCORERS.get_or_init(|| Mutex::new(HashMap::new()))
}

#[unsafe(no_mangle)]
pub extern "system" fn Java_com_pulsewatch_scoring_NativeScorer_nativeNew(
    _env: JNIEnv,
    _class: JClass,
    baseline_window_secs: jdouble,
    sensitivity: jfloat,
) -> jlong {
    let baseline_window = match Duration::try_from_secs_f64(baseline_window_secs) {
        Ok(duration) if !duration.is_zero() => duration,
        _ => return 0, // Kotlin treats zero as construction failure
    };
    match AlertScorer::new(baseline_window, sensitivity) {
        Ok(scorer) => {
            let handle = NEXT_HANDLE.fetch_add(1, Ordering::Relaxed);
            registry().lock().expect("scorer registry mutex poisoned").insert(handle, scorer);
            handle
        }
        Err(_) => 0,
    }
}

#[unsafe(no_mangle)]
pub extern "system" fn Java_com_pulsewatch_scoring_NativeScorer_nativeScore(
    mut env: JNIEnv,
    _class: JClass,
    handle: jlong,
    shard_label: JString,
    value: jdouble,
    timestamp_unix_ms: jlong,
) -> jfloat {
    let _label: String = match env.get_string(&shard_label) {
        Ok(s) => s.into(),
        Err(_) => {
            let _ = env.throw_new("java/lang/IllegalArgumentException", "shard_label was not valid UTF-8");
            return 0.0;
        }
    };
    let mut scorers = registry().lock().expect("scorer registry mutex poisoned");
    let scorer = match scorers.get_mut(&handle) {
        Some(scorer) => scorer,
        None => {
            let _ = env.throw_new("java/lang/IllegalStateException", "scorer already closed or invalid handle");
            return 0.0;
        }
    };
    let sample = Sample { value, timestamp_unix_ms };
    // Every ScoringError variant is mapped explicitly: adding a new variant
    // to AlertScorer without updating this match is a compile error.
    match scorer.score(sample) {
        Ok(score) => score as jfloat,
        Err(ScoringError::SensitivityOutOfRange) => {
            let _ = env.throw_new("java/lang/IllegalStateException", "sensitivity out of range");
            0.0
        }
        Err(ScoringError::InvalidBaselineWindow) => {
            let _ = env.throw_new("java/lang/IllegalStateException", "baseline window is invalid");
            0.0
        }
        Err(ScoringError::EmptyWindow) => {
            let _ = env.throw_new("java/lang/IllegalStateException", "scoring window is empty");
            0.0
        }
        Err(ScoringError::NonFiniteValue) => {
            let _ = env.throw_new("java/lang/IllegalArgumentException", "value must be finite");
            0.0
        }
    }
}

#[unsafe(no_mangle)]
pub extern "system" fn Java_com_pulsewatch_scoring_NativeScorer_nativeFree(
    _env: JNIEnv,
    _class: JClass,
    handle: jlong,
) {
    // A missing/already-removed key is a harmless no-op, so a double-free
    // from Kotlin can never reach an already-freed Rust allocation.
    registry().lock().expect("scorer registry mutex poisoned").remove(&handle);
}

The Kotlin side declares the matching external functions and loads the library once, in a companion object, before any instance is constructed. Its shape is unchanged by the registry rewrite above — Kotlin only ever holds an opaque Long either way — but the check(handle != 0L) guard is now an optimization, not the safety mechanism: even if two threads race past it, the Rust-side registry lookup is what actually prevents use-after-free, by returning a clean exception for a concurrently-freed handle instead of touching memory. File: path/to/pulsewatch/android/app/src/main/kotlin/com/pulsewatch/scoring/NativeScorer.kt (new file, complete):

// android/app/src/main/kotlin/com/pulsewatch/scoring/NativeScorer.kt
package com.pulsewatch.scoring

class NativeScorer(baselineWindowSecs: Double, sensitivity: Float) : AutoCloseable {
    private var handle: Long = nativeNew(baselineWindowSecs, sensitivity)

    fun score(shardLabel: String, value: Double, timestampUnixMs: Long): Float {
        check(handle != 0L) { "scorer already closed" }
        return nativeScore(handle, shardLabel, value, timestampUnixMs)
    }

    override fun close() {
        if (handle != 0L) {
            nativeFree(handle)
            handle = 0L
        }
    }

    private external fun nativeNew(baselineWindowSecs: Double, sensitivity: Float): Long
    private external fun nativeScore(handle: Long, shardLabel: String, value: Double, timestampUnixMs: Long): Float
    private external fun nativeFree(handle: Long)

    companion object {
        init {
            System.loadLibrary("pulsewatch_scoring")
        }
    }
}
New syntaxWhy it exists
Java_com_pulsewatch_scoring_NativeScorer_nativeNewJNI's required naming convention, Java_<package>_<Class>_<method>, is how the JVM locates the native symbol at loadLibrary time; it must match the Kotlin external fun name exactly.
extern "system"Selects the correct calling convention across platforms (notably Windows), which JNI requires instead of a hard-coded "C".
OnceLock<Mutex<HashMap<jlong, AlertScorer>>>A concurrency-safe handle registry instead of a raw boxed pointer: Kotlin only ever holds an opaque Long key, the lock makes concurrent nativeScore/nativeFree calls serialize, and a handle nativeFree removes simply stops resolving instead of leaving a dangling pointer another thread could dereference.
env.get_string(...)The jni crate's safe wrapper around GetStringUTFChars/ReleaseStringUTFChars; it copies the Kotlin string into an owned Rust String, a real per-call cost worth knowing about.
Exhaustive match on ScoringErrorEvery variant from Lesson 19's AlertScorer maps to a distinct Java exception type and message; there is no wildcard arm, so a new variant fails to compile until handled here too.
class NativeScorer : AutoCloseableMirrors the explicit close-not-finalize discipline from Part 4's UniFFI callout: the native handle is only reclaimed when close() runs, not when the JVM garbage-collects the Kotlin object.

Part 4: UniFFI Kotlin — the product-facing API

Raw JNI glue explains the mechanism; the actual Pulsewatch mobile API should be generated, not hand-written. The same reuse rule applies here: the UniFFI object wraps AlertScorer per shard behind a mutex, and maps every ScoringError variant explicitly through a From impl rather than inventing an incompatible error type. A UniFFI object is a proc-macro-only crate — there is no UDL file here — so it needs one setup call, two library outputs (a cdylib the host machine can load to generate bindings from, and a staticlib Android links per ABI in Part 5), and a small local uniffi-bindgen binary, because UniFFI's own tutorial notes that the real uniffi-bindgen executable requires an unstable Cargo feature outside of nightly. // crates/pulsewatch-scoring/src/mobile.rs
use std::collections::HashMap;
use std::sync::Mutex;
use std::time::Duration;
use crate::{AlertScorer, Sample, ScoringError};

#[derive(uniffi::Error, Debug)]
pub enum MobileScoringError {
    InvalidSensitivity,
    InvalidBaselineWindow,
    EmptyWindow,
    NonFiniteValue,
}

// Explicit, exhaustive mapping from Lesson 19's ScoringError -- no `_` arm,
// so a new AlertScorer error variant fails to compile until handled here.
impl From<ScoringError> for MobileScoringError {
    fn from(err: ScoringError) -> Self {
        match err {
            ScoringError::SensitivityOutOfRange => MobileScoringError::InvalidSensitivity,
            ScoringError::InvalidBaselineWindow => MobileScoringError::InvalidBaselineWindow,
            ScoringError::EmptyWindow => MobileScoringError::EmptyWindow,
            ScoringError::NonFiniteValue => MobileScoringError::NonFiniteValue,
        }
    }
}

/// The same per-shard adapter idea as Part 3's handle registry, kept
/// behind a mutex here because UniFFI objects may be called from multiple
/// Kotlin coroutines/threads, unlike the single-threaded JNI handle above.
#[derive(uniffi::Object)]
pub struct MobileScorer {
    shards: Mutex<HashMap<String, AlertScorer>>,
    baseline_window: Duration,
    sensitivity: f32,
}

#[uniffi::export]
impl MobileScorer {
    #[uniffi::constructor]
    pub fn new(baseline_window_secs: f64, sensitivity: f32) -> Result<Self, MobileScoringError> {
        let baseline_window = Duration::try_from_secs_f64(baseline_window_secs)
            .map_err(|_| MobileScoringError::InvalidBaselineWindow)?;
        if baseline_window.is_zero() {
            return Err(MobileScoringError::InvalidBaselineWindow);
        }
        AlertScorer::new(baseline_window, sensitivity)?; // validate sensitivity once, up front
        Ok(Self { shards: Mutex::new(HashMap::new()), baseline_window, sensitivity })
    }

    pub fn score(&self, shard_label: String, value: f64, timestamp_unix_ms: i64) -> Result<f32, MobileScoringError> {
        let mut shards = self.shards.lock().expect("scorer registry mutex poisoned");
        let scorer = shards.entry(shard_label).or_insert_with(|| {
            AlertScorer::new(self.baseline_window, self.sensitivity)
                .expect("sensitivity already validated in MobileScorer::new")
        });
        Ok(scorer.score(Sample { value, timestamp_unix_ms })?)
    }
}
// Generated Kotlin usage looks like ordinary Kotlin
val scorer = MobileScorer(300.0, 0.62f)
try {
    val score = scorer.score("shard-42", 0.87, 1_726_600_000_000L)
} catch (e: MobileScoringException.NonFiniteValue) {
    // handle
} finally {
    scorer.close()
}

Integrating the generation step into Gradle runs uniffi-bindgen as a build task per variant, so the Kotlin source stays in sync with the Rust API on every build rather than being copied in by hand.

⚠️
Generated Kotlin objects have an explicit lifecycle, not a reliable finalizer

UniFFI's Kotlin bindings implement Disposable/AutoCloseable with a close() method that must be called explicitly to reclaim the underlying Rust resources — Kotlin's garbage collector will not do this reliably on its own. Lists and maps of interface objects are not auto-closed either; each contained object must be closed individually. Plan for this the same way you plan for RAII scope exit in C++.

Part 5: Android packaging — per-ABI .so and loadLibrary

Android ships several ABIs (arm64-v8a, armeabi-v7a, x86_64, ...), each needing its own compiled shared library, cross-compiled separately from the host build Part 4 and Part 6 use to generate Kotlin bindings — the same "host cdylib for generation, per-target build for shipping" split this course returns to in Lesson 22 for iOS. Raw cargo build --target aarch64-linux-android needs a working NDK linker on PATH for every target, which cargo-ndk (installed in Follow-along setup) configures automatically and writes straight into the jniLibs layout Android expects, so no manual cp step is needed. From path/to/pulsewatch/ (the workspace root):

cargo ndk -t arm64-v8a -o android/app/src/main/jniLibs build --release -p pulsewatch-scoring

This writes android/app/src/main/jniLibs/arm64-v8a/libpulsewatch_scoring.so directly. Add -t armeabi-v7a -t x86_64 (repeat -t per ABI) to build additional ABIs into the same output tree in one invocation. System.loadLibrary("pulsewatch_scoring"), typically called once from a companion object init block, resolves to the correct per-ABI library at runtime. UniFFI's own documentation is explicit that it generates the Kotlin bindings, not this packaging step — the cross-compilation, jniLibs layout, and Gradle wiring stay your responsibility.

Where useful for contrast: JNA (Java Native Access) avoids writing JNI glue entirely by reflecting over a plain C ABI at runtime, at the cost of runtime dispatch overhead and weaker compile-time checking. Pulsewatch prefers UniFFI's compile-time-generated, checked JNI glue for its product API instead.

Knowledge check

1. Why must a global JNI reference be explicitly deleted while a local reference does not?

Answer: Local references are automatically freed by the JVM at the end of the native call. Global references are meant to outlive the call, so they leak unless code explicitly calls DeleteGlobalRef.

2. Why call AttachCurrentThread before using JNIEnv from a Rust-spawned OS thread?

Answer: JNIEnv is only valid on threads that are attached to the JVM. A raw OS thread has no valid JNIEnv until it is attached, and must detach before exiting.

3. What does UniFFI actually generate for Android, and what does it not generate?

Answer: It generates the Kotlin binding source that calls into the compiled Rust library. It does not cross-compile or copy the per-ABI .so files, and it does not write the Gradle packaging — those remain your responsibility.

4. Why prefer UniFFI's generated JNI glue over JNA for the Pulsewatch product API?

Answer: UniFFI's glue is generated at build time and checked against the real Rust API. JNA reflects over a plain C ABI at runtime, trading that compile-time checking for slower, less-verified dispatch.

5. Why does Part 3 keep every AlertScorer in a mutex-guarded HashMap<jlong, AlertScorer> instead of boxing a raw pointer into the jlong handle the way Lesson 19's PwScorer does?

Answer: A raw boxed pointer has no protection against one thread calling nativeFree (freeing it) while another concurrently calls nativeScore on the same handle — a use-after-free. Looking the handle up in a locked map instead makes those calls serialize, and once nativeFree removes the entry, a stale handle simply fails a map lookup and throws a clean exception instead of dereferencing freed memory.

Recap and decision rules

Learning JNI's raw model?            Study JNIEnv, local/global refs, and threads first
Writing Rust-side JNI by hand?       Use the jni crate over raw FFI
Building the product API?            Generate it with UniFFI Kotlin
New native thread calls into Kotlin? Attach it to the JVM first, detach before exit
Shipping to Android?                 Cross-compile per ABI, place under jniLibs, loadLibrary once
Tempted to skip JNI entirely?        JNA trades compile-time checks for runtime reflection
