Lesson 18 · 30 minutes

Performance & Unsafe Verification

Benchmark Pulsewatch's render path against a saved baseline with Criterion, read a flamegraph, and re-verify the Lesson 8 unsafe wrapper with Miri instead of trusting it indefinitely.

By the end: you can benchmark against a saved baseline instead of a single timing, explain why Criterion is preferred over the unstable built-in #[bench] on stable CI, read a flamegraph's frame widths against a baseline, and re-verify unsafe code with Miri while understanding it as dynamic, not exhaustive, evidence.

Follow-along setup

This lesson starts from the Pulsewatch workspace as Lessons 7–17 left it: crates/pulsewatch-core (the Probe trait, Millis, Sample, and the Lesson 8 copy_probe_bytes unsafe wrapper), plus the [profile.release] section Lesson 17 added to the workspace root Cargo.toml. This lesson adds a benchmark, tunes that release profile further, and re-verifies existing unsafe code; it does not remove anything.

cd path/to/pulsewatch

path/to is a placeholder: replace the whole segment with wherever you checked out the Pulsewatch workspace, for example cd ~/dev/pulsewatch. Unless a step says otherwise, run every cargo command below from this workspace root, the directory containing the top-level Cargo.toml. Part 3 additionally requires cargo install flamegraph (run from anywhere; it installs a cargo subcommand, not a project dependency) and, on Linux, a working perf install; Part 5 requires rustup +nightly component add miri (run from anywhere).

Part 1: measure before you optimize

A single ad hoc timing (one Instant::now() before and after) is noise: OS scheduling jitter, CPU frequency scaling, and cache state all move a one-shot number around by far more than most real optimizations. Treat performance work as evidence against a baseline, not a one-off measurement, and always benchmark an optimized build:

Cargo.toml (workspace root) — replace the [profile.release] section Lesson 17 added, with these additional keys
[profile.release]
opt-level = 3
lto = "thin"
codegen-units = 1   # fewer codegen units, more cross-function optimization, slower to compile
debug = true        # keep symbols for profiling; does not disable optimizations

A debug build's unoptimized code, overflow checks, and debug_assert!s make any timing from it meaningless for judging real performance.

Part 2: Criterion vs the unstable built-in bencher

Nightly Rust has an unstable, built-in #[bench] harness behind the test feature. Its bencher repeatedly runs the measured closure and reports a summary such as nanoseconds per iteration, but the API remains nightly-only and offers less regression-analysis support. Criterion.rs works on stable Rust, performs statistical analysis across repeated samples, reports confidence intervals and likely outliers, and can save a named baseline to compare future runs against. Register it first:

crates/pulsewatch-core/Cargo.toml — append to the existing [dev-dependencies] table (the one Lesson 16 added proptest to)
criterion = { version = "0.5", features = ["html_reports"] }
crates/pulsewatch-core/Cargo.toml — append a new [[bench]] table (add after [dev-dependencies])
[[bench]]
name = "render"
harness = false
crates/pulsewatch-core/benches/render.rs — create
// pulsewatch-core/benches/render.rs
use criterion::{black_box, criterion_group, criterion_main, Criterion};
use pulsewatch_core::{Millis, Sample};

fn naive_render(samples: &[Sample]) -> String {
    samples.iter().map(|s| format!("{}: {:03}ms\n", s.source, s.latency.get())).collect()
}

fn buffered_render(samples: &[Sample]) -> String {
    use std::fmt::Write;
    let mut out = String::with_capacity(samples.len() * 24);
    for s in samples {
        let _ = writeln!(out, "{}: {:03}ms", s.source, s.latency.get());
    }
    out
}

fn bench_render(c: &mut Criterion) {
    let samples: Vec<Sample> = (0..1_000)
        .map(|i| Sample { source: format!("probe-{i}"), latency: Millis::new(i as u64) })
        .collect();
    c.bench_function("naive_render", |b| b.iter(|| naive_render(black_box(&samples))));
    c.bench_function("buffered_render", |b| b.iter(|| buffered_render(black_box(&samples))));
}

criterion_group!(benches, bench_render);
criterion_main!(benches);

Run both benchmark passes from the workspace root:

cargo bench -p pulsewatch-core -- --save-baseline main
# ... apply the buffered_render optimization ...
cargo bench -p pulsewatch-core -- --baseline main

The second run reports the percentage change against the saved main baseline for each function, with a confidence interval, not just a single new number to eyeball against memory.

Part 3: reading a flamegraph

A flamegraph turns sampled stack traces into stacked, horizontal frames: each frame's width is the fraction of samples where that function was on the stack, and stacking shows the call chain. A wide frame spent more sampled time; a narrow one did not. It still needs a baseline — a wide frame in the only profile you have ever taken looks the same whether it is expected or a regression. From the workspace root, with cargo install flamegraph already run once (from anywhere):

cargo flamegraph -p pulsewatch-core --bench render -- --bench

Read width first, not color; most flamegraph tools color frames only for visual separation between call stacks, not to encode "hot" vs "cold" by hue.

Part 4: heap allocation as a cost, not just CPU time

naive_render's format! call allocates a new String per sample; buffered_render allocates once via String::with_capacity and reuses it. A CPU-time benchmark can already surface this difference, but a dedicated allocation counter (for example, wrapping the global allocator to count calls in a test) makes the allocation-count claim itself measurable rather than inferred from timing alone.

Part 5: Miri and sanitizers verify exercised paths, not all inputs

Lesson 8's copy_probe_bytes unsafe wrapper needs re-verification whenever its surrounding code changes. Miri is an interpreter that catches undefined behavior, out-of-bounds access, use-after-free, invalid pointer arithmetic, for whichever inputs your test actually exercises. From the workspace root, with the miri component already installed on nightly (rustup +nightly component add miri, run from anywhere):

cargo +nightly miri test -p pulsewatch-core copy_probe_bytes

Sanitizers (address, memory, thread) are a nightly, unstable Cargo flag that instruments a real compiled binary rather than interpreting it, trading Miri's slower, exhaustive-feeling checking for closer-to-native speed. This example targets Linux; substitute your own target triple if different:

RUSTFLAGS="-Z sanitizer=address" cargo +nightly test -p pulsewatch-core --target x86_64-unknown-linux-gnu
⚠️
Dynamic checkers, not proofs

Miri and sanitizers are dynamic checkers: they only see undefined behavior along the code paths and input values your tests actually exercise. A clean Miri run on copy_probe_bytes's existing tests does not prove the function is safe for every ptr/len pair a caller could someday pass; it proves nothing went wrong for the inputs tested. Treat both as strong evidence, not a formal proof of the absence of undefined behavior.

Worked Pulsewatch increment

Pulsewatch's render path now has a Criterion benchmark comparing the original per-row-allocating naive_render against a buffer-reusing buffered_render, a saved main baseline to measure any future change against, a flamegraph confirming which frame the time actually moved from, and a re-run of Miri over the Lesson 8 copy_probe_bytes wrapper now that surrounding code has changed.

🧭
Stability and production boundary

A benchmark win on the exact 1,000-sample input generated here does not guarantee a win at every batch size, and a clean Miri run over today's tests does not certify copy_probe_bytes safe for every future caller. Re-benchmark against the saved baseline and re-run Miri whenever the hot path or the unsafe wrapper's surrounding assumptions change, rather than trusting one past result indefinitely.

Active exercise

  1. From the workspace root, run cargo bench -p pulsewatch-core -- --save-baseline main against the unmodified naive_render/buffered_render pair. Expected evidence: Criterion prints a report for both functions and writes it under target/criterion/, with no --baseline comparison yet since main was just created.
  2. In crates/pulsewatch-core/benches/render.rs (replace the body of buffered_render), pre-size the buffer more precisely, for example replacing samples.len() * 24 with a capacity computed from the actual formatted width, then save the file.
  3. From the workspace root, run cargo bench -p pulsewatch-core -- --baseline main. Expected evidence: a Criterion report showing a percentage change for buffered_render against the main baseline, with a confidence interval, not just a single new number.
  4. From the workspace root, run cargo flamegraph -p pulsewatch-core --bench render -- --bench. Expected evidence: a flamegraph.svg file is written to the workspace root; open it and identify which frame's width shrank compared to your mental model of step 1's report.
  5. From the workspace root, run cargo +nightly miri test -p pulsewatch-core copy_probe_bytes. Expected evidence: the command reports the existing copy_probe_bytes tests passing under Miri with no undefined-behavior diagnostics, confirming this lesson's benchmark and profile changes did not introduce any.
  6. Write one sentence, as a comment appended to the top of the #[cfg(test)] mod tests block in crates/pulsewatch-core/src/unsafe_probe.rs, describing what that clean Miri run does and does not prove about copy_probe_bytes.

Knowledge check

1. Why is a single before/after Instant::now() timing not sufficient evidence that an optimization helped?

Answer: Scheduling jitter, CPU frequency scaling, and cache state can move a one-shot timing by more than many real optimizations change; you need repeated samples and a saved baseline to distinguish a real effect from noise.

2. Why is Criterion generally preferred over the nightly #[bench] harness for a project that runs its CI on stable Rust?

Answer: #[bench] is gated behind the unstable test feature and only available on nightly. Criterion works on stable Rust and adds statistical comparison, confidence intervals, outlier reporting, and saved baselines for regression analysis.

3. A flamegraph shows one very wide frame. What do you still need before concluding it is a performance problem?

Answer: A baseline: a wide frame just means that function used a large share of sampled time in this one profile; without a prior profile or expectation to compare against, you cannot tell if that is normal or a regression.

4. A Miri run over copy_probe_bytes's existing tests is clean. What exactly does that prove, and what does it not prove?

Answer: It proves no undefined behavior was detected for the pointer/length inputs the existing tests actually exercised; it does not prove the function is safe for every ptr/len pair a future caller could pass, since Miri and sanitizers are dynamic checkers, not formal proofs.

Recap and decision rules

About to trust a single before/after timing?     Don't; benchmark repeatedly against a saved baseline
CI must run on stable Rust?                       Use Criterion, not nightly #[bench]
Flamegraph shows a wide frame?                     Confirm against a baseline before calling it a problem
Need allocation counts, not just CPU time?         Add a dedicated allocation counter, don't infer from timing alone
Changed code near an unsafe wrapper?               Re-run Miri (and sanitizers if available) on it
Miri/sanitizers came back clean?                    Evidence for exercised paths only, not a safety proof for all inputs
