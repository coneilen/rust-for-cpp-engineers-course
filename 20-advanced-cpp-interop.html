Lesson 20 · 30 minutes

Advanced C++ Interop: Choosing a Bridge

Move beyond Lesson 19's raw C ABI: evaluate bindgen, cxx, autocxx, and Crubit for Pulsewatch's remaining batch-scoring boundary, and bridge exceptions, ownership, and pinning correctly.

By the end: You can pick the right interop tool for a given C++↔Rust boundary, use cxx's #[cxx::bridge] to share owned/borrowed types and a C++ callback safely, wire build.rs/cc linking, and explain why autocxx and Crubit are not universal, mechanical converters today.

Part 1: why the raw ABI stops being enough

Lesson 19's boundary carries primitives and one opaque handle — enough for a single scalar sample. The remaining C++ ingestion call sites now need three things a hand-rolled extern "C" surface makes painful: submitting a batch of samples in one call, passing a std::string shard label for logging, and registering a C++ callback invoked when a score crosses an alert threshold. Hand-writing pointer-plus-length conventions and status-code plumbing for all of that is exactly the kind of repetitive, error-prone glue a curated bridge generator exists to remove.

Part 2: bindgen — importing an existing C/C++ header

bindgen parses C or C++ headers with libclang and emits raw, unsafe Rust FFI declarations. It is one-directional — importing an existing C/C++ API into Rust — and it does not produce a safe surface; you still wrap the generated items by hand, the same discipline as Lesson 19. File: path/to/pulsewatch/crates/pulsewatch-scoring/build.rs (new file — this excerpt shows only the bindgen half; Part 4 appends the cxx_build half to the same fn main()). Cargo always runs a crate's build.rs with its current directory set to that crate's own manifest directory, regardless of where cargo build was invoked from, so the relative paths below resolve against crates/pulsewatch-scoring/ even though every command in this lesson runs from the workspace root:

Part 3: cxx — a curated, bidirectional bridge

cxx defines one shared contract that generates matching Rust and C++ code from a single declaration, checked at build time, rather than trusting a hand-maintained header to stay in sync with hand-maintained Rust declarations. File: path/to/pulsewatch/crates/pulsewatch-scoring/src/ffi.rs (new file — this is the top of the file, the bridge declaration; the implementation below is an excerpt of the rest of the same file):

// crates/pulsewatch-scoring/src/ffi.rs (new file, top half — the #[cxx::bridge] declaration)
#[cxx::bridge(namespace = "pulsewatch")]
mod ffi {
    struct TimestampedSample {
        value: f64,
        timestamp_unix_ms: i64,
    }

    struct ScoredSample {
        timestamp_unix_ms: i64,
        score: f32,
    }

    extern "Rust" {
        type BatchScorer;

        fn new_batch_scorer(baseline_window_secs: f64, sensitivity: f32) -> Result<Box<BatchScorer>>;
        fn score_batch(
            scorer: &mut BatchScorer,
            shard_label: &str,
            samples: &[TimestampedSample],
            notifier: Pin<&mut AlertNotifier>,
        ) -> Result<Vec<ScoredSample>>;
    }

    unsafe extern "C++" {
        include!("pulsewatch/alert_notifier.h");
        type AlertNotifier;

        fn notify_if_over_threshold(self: Pin<&mut AlertNotifier>, sample: &ScoredSample) -> bool;
    }
}

The declaration alone only sets the contract; the implementation below it backs BatchScorer with the same AlertScorer core from Lesson 19, so the sliding-window scoring logic is not duplicated for the batch path. File: path/to/pulsewatch/crates/pulsewatch-scoring/src/ffi.rs (same file, continued — append this below the bridge declaration above; together the two blocks are the complete file):

// crates/pulsewatch-scoring/src/ffi.rs (new file, bottom half — continues directly below the bridge declaration)
use crate::{AlertScorer, Sample, ScoringError};
use std::time::Duration;

// cxx converts a returned Err into a thrown C++ exception using this impl.
impl std::fmt::Display for ScoringError {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        match self {
            ScoringError::SensitivityOutOfRange => write!(f, "sensitivity out of range"),
            ScoringError::InvalidBaselineWindow => write!(f, "baseline window must be finite and positive"),
            ScoringError::EmptyWindow => write!(f, "scoring window is empty"),
            ScoringError::NonFiniteValue => write!(f, "sample value is not finite"),
        }
    }
}

/// One `BatchScorer` is created per shard and reused across many
/// `score_batch` calls; it owns a single Lesson 19 `AlertScorer`, so the
/// sliding window persists between batches exactly as it would for
/// single-sample calls through `pw_scorer_score`.
pub struct BatchScorer {
    inner: AlertScorer,
}

fn new_batch_scorer(baseline_window_secs: f64, sensitivity: f32) -> Result<Box<BatchScorer>, ScoringError> {
    // Fallible conversion also rejects finite values too large for Duration.
    // Reject tiny positive inputs that round to Duration::ZERO.
    let baseline_window = Duration::try_from_secs_f64(baseline_window_secs)
        .map_err(|_| ScoringError::InvalidBaselineWindow)?;
    if baseline_window.is_zero() {
        return Err(ScoringError::InvalidBaselineWindow);
    }
    let inner = AlertScorer::new(baseline_window, sensitivity)?;
    Ok(Box::new(BatchScorer { inner }))
}

fn score_batch(
    scorer: &mut BatchScorer,
    shard_label: &str,
    samples: &[ffi::TimestampedSample],
    mut notifier: std::pin::Pin<&mut ffi::AlertNotifier>,
) -> Result<Vec<ffi::ScoredSample>, ScoringError> {
    let mut scored = Vec::with_capacity(samples.len());
    for sample in samples {
        // Real per-sample timestamps from the caller, not a synthesized
        // offset -- this scorer is persistent across calls (Part 2), so
        // resetting timestamps to zero each batch would corrupt the
        // sliding window's eviction logic on every call after the first.
        let score = scorer.inner.score(Sample {
            value: sample.value,
            timestamp_unix_ms: sample.timestamp_unix_ms,
        })?;
        let scored_sample = ffi::ScoredSample {
            timestamp_unix_ms: sample.timestamp_unix_ms,
            score,
        };
        // `notifier` is borrowed for exactly this call and reborrowed via
        // `as_mut()` on each iteration — cxx pins it so Rust can never
        // stash the reference past score_batch's return, keeping the C++
        // object's lifetime and ownership entirely with the caller.
        if notifier.as_mut().notify_if_over_threshold(&scored_sample) {
            eprintln!("shard {shard_label}: score {} crossed the alert threshold", scored_sample.score);
        }
        scored.push(scored_sample);
    }
    Ok(scored)
}

New syntaxWhy it exists
#[cxx::bridge]One declaration generates both the Rust module and a matching C++ header/source; the two sides cannot silently drift the way a hand-maintained header can.
struct TimestampedSample { ... } / ScoredSample { ... } (shared)Plain-data types with a layout cxx generates identically on both sides, crossing by value in either direction. &[TimestampedSample] maps to C++'s rust::Slice<const TimestampedSample>, carrying the caller's real per-sample timestamp instead of synthesizing one Rust-side.
extern "Rust" { type BatchScorer; ... }Exposes a Rust type and its functions to C++, generating the C++-side wrapper class automatically. The real pub struct BatchScorer and its functions live in ordinary Rust below the bridge macro, not inside it.
unsafe extern "C++" { type AlertNotifier; ... }Imports an existing C++ type into Rust as an opaque type usable only through the declared methods.
notifier: Pin<&mut AlertNotifier> as a score_batch parameterPasses the caller's C++ notifier into Rust for exactly one call. C++ objects are not guaranteed movable the way Rust values are, so cxx requires Pin for mutable access; because it is a borrowed parameter, not a stored field, its lifetime and ownership stay entirely with the C++ caller.
notifier.as_mut() inside the loopCalling a Pin<&mut T> method through self: Pin<&mut T> consumes that pin by value; reborrowing with as_mut() is what allows calling it again on the next sample in the same batch.
Result<...> in the bridge signaturecxx converts a thrown C++ exception into a Rust Err, and a returned Rust Err into a thrown C++ exception via the error type's Display impl, instead of hand-rolled status codes.

AlertNotifier is an ordinary, pre-existing C++ class — cxx imports it, it does not generate it. File: path/to/pulsewatch/crates/pulsewatch-scoring/include/pulsewatch/alert_notifier.h (new file — a compact but complete header, not an excerpt):

// crates/pulsewatch-scoring/include/pulsewatch/alert_notifier.h (new file)
#pragma once
#include "pulsewatch-scoring/src/ffi.rs.h"  // generated by cxx_build; declares ScoredSample

namespace pulsewatch {

class AlertNotifier {
public:
    explicit AlertNotifier(double threshold) : threshold_(threshold) {}

    // Invoked once per scored sample from score_batch (Part 3); returns
    // true when this sample crossed the threshold and a notification was
    // sent, so the Rust side can log it.
    bool NotifyIfOverThreshold(const ScoredSample& sample);

    int NotificationsSent() const { return notifications_sent_; }

private:
    double threshold_;
    int notifications_sent_ = 0;
};

}  // namespace pulsewatch

File: path/to/pulsewatch/crates/pulsewatch-scoring/src/alert_notifier.cc (new file — a compact but complete implementation, not an excerpt):

// crates/pulsewatch-scoring/src/alert_notifier.cc (new file)
#include "pulsewatch/alert_notifier.h"

namespace pulsewatch {

bool AlertNotifier::NotifyIfOverThreshold(const ScoredSample& sample) {
    if (sample.score < threshold_) {
        return false;
    }
    ++notifications_sent_;
    // The existing alerting pipeline call goes here; the Part 6 smoke test
    // only checks the return value and NotificationsSent().
    return true;
}

}  // namespace pulsewatch
🧩
Exception/panic conversion has a limit

cxx's Result conversion only helps for expected, declared C++ exceptions and Rust errors. A genuine Rust panic unwinding across a cxx boundary still aborts, exactly like the raw extern "C" boundary in Lesson 19 — this bridge does not remove the need for panic discipline, it removes the need to hand-roll status codes for expected failures.

Part 4: build.rs and cc linking

cxx_build::bridge runs the cxxbridge code generator and compiles the resulting C++ shim through the cc crate, so Cargo alone drives the whole cross-language build for this bridge — no separate CMake invocation is required just to compile it. File: path/to/pulsewatch/crates/pulsewatch-scoring/build.rs (append inside the same fn main() from Part 2, after the existing bindgen::Builder block; shown here without the surrounding fn main() { } to avoid duplicating it):

// crates/pulsewatch-scoring/build.rs (add inside the existing fn main(), after Part 2's bindgen block)
cxx_build::bridge("src/ffi.rs")
    .file("src/alert_notifier.cc")
    .include("include") // resolves include!("pulsewatch/alert_notifier.h")
    .flag_if_supported("-std=c++17")
    .compile("pulsewatch-batch-bridge");

println!("cargo:rerun-if-changed=src/ffi.rs");
println!("cargo:rerun-if-changed=src/alert_notifier.cc");
println!("cargo:rerun-if-changed=include/pulsewatch/alert_notifier.h");

Part 5: autocxx and Crubit — check status before you plan around them

⚠️
autocxx is not the recommended entry point for new work

autocxx's own README now tells new users to consider cxx or Crubit instead of autocxx. Treat autocxx as retired guidance for new Pulsewatch bridges, not a live third option.

Crubit is Google's actively developed, bidirectional C++/Rust interop project — but it documents its own incomplete feature and build-system coverage on a public status page. Check that page for the specific feature and build system a use case needs before depending on it; do not assume general availability.

ToolWhat it actually is today
bindgenOne-directional C/C++-to-Rust import; low-level, unsafe output you wrap by hand.
cxxCurated, bidirectional, statically checked bridge; the default choice for a genuinely two-way boundary.
autocxxIts own maintainers direct new users to cxx or Crubit instead; not a safe default for new deployments.
CrubitActive and bidirectional, but its status page documents which features and build systems are and are not yet supported — verify per use case.
🧭
None of these tools convert arbitrary C++ mechanically

Templates, multiple inheritance, and complex macros are not automatically translated end to end by any of these generators. Each bridges a deliberately narrow, hand-chosen seam — the same seam-first discipline as Lesson 19, not a universal-coverage promise.

Part 6: exercise — bridge batch scoring with cxx

Add the #[cxx::bridge] declaration and the BatchScorer/score_batch implementation from Part 3 to pulsewatch-scoring, implement the matching C++ AlertNotifier from earlier in this Part, and wire build.rs from Part 4. File: path/to/pulsewatch/crates/pulsewatch-scoring/tests/batch_bridge_smoke.cc (new file — complete, not an excerpt; it warms up the scorer once because, like Lesson 19, the very first sample a fresh scorer ever sees only seeds the baseline window and reports EmptyWindow rather than a score):

// crates/pulsewatch-scoring/tests/batch_bridge_smoke.cc (new file)
#include "pulsewatch-scoring/src/ffi.rs.h"
#include "pulsewatch/alert_notifier.h"
#include <cassert>
#include <cstdio>
#include <vector>

namespace {
std::vector<pulsewatch::TimestampedSample> BuildFixtureBatch() {
    std::vector<pulsewatch::TimestampedSample> batch;
    batch.reserve(128);
    std::int64_t t = 1758067201000;
    for (int i = 0; i < 128; ++i) {
        // A flat baseline of 100.0 with three deliberate spikes to 500.0,
        // one second apart -- well inside the 300s baseline window, so
        // nothing is evicted before the batch ends.
        double value = (i == 40 || i == 80 || i == 120) ? 500.0 : 100.0;
        batch.push_back({value, t});
        t += 1000;
    }
    return batch;
}
}  // namespace

int main() {
    auto scorer = pulsewatch::new_batch_scorer(/*baseline_window_secs=*/300.0, /*sensitivity=*/0.62);
    pulsewatch::AlertNotifier notifier(/*threshold=*/0.8);

    // Warm-up: a fresh scorer's very first sample only seeds the baseline
    // and cannot itself be scored (Lesson 19's EmptyWindow rule), so cxx
    // converts that one expected condition into a C++ exception here.
    // This deliberately swallows it before measuring the real batch below.
    try {
        std::vector<pulsewatch::TimestampedSample> warm_up{{100.0, 1758067200000}};
        rust::Slice<const pulsewatch::TimestampedSample> warm_up_slice(warm_up.data(), warm_up.size());
        pulsewatch::score_batch(*scorer, "fleet-a", warm_up_slice, notifier);
    } catch (const std::exception&) {
        // Expected exactly once, for the warm-up sample only.
    }

    std::vector<pulsewatch::TimestampedSample> batch = BuildFixtureBatch();
    rust::Slice<const pulsewatch::TimestampedSample> slice(batch.data(), batch.size());
    auto scored = pulsewatch::score_batch(*scorer, "fleet-a", slice, notifier);

    assert(scored.size() == batch.size());
    std::printf("scored %zu/%zu samples, %d notifications sent\n",
                scored.size(), batch.size(), notifier.NotificationsSent());
    return 0;
}

Knowledge check

1. Why choose cxx over bindgen for the batch-scoring boundary?

Answer: cxx defines a bidirectional, statically checked shared surface with matching layouts generated on both sides, plus safe exception/Result conversion. bindgen only imports a one-directional, unsafe C-facing surface that you must wrap by hand.

2. Why does notify_if_over_threshold take self: Pin<&mut AlertNotifier>, and why is it passed into score_batch as a parameter instead of stored on BatchScorer?

Answer: C++ objects are not guaranteed movable/relocatable the way Rust values are, so cxx pins C++-owned types for mutable access. Passing it as a per-call parameter (reborrowed with as_mut() for each sample) keeps its lifetime and ownership entirely with the C++ caller instead of letting BatchScorer stash a reference past the call.

3. Should Pulsewatch adopt autocxx for this new bridge?

Answer: No. autocxx's own README now points new users to cxx or Crubit; it is not a safe default choice for new deployments.

4. Is Crubit a ready, mechanical replacement for a hand-chosen interop seam today?

Answer: Not necessarily. It is actively developed, but its own status page documents current feature and build-system coverage; check it for the specific need before depending on it.

5. Why does new_batch_scorer use Duration::try_from_secs_f64 and then reject Duration::ZERO?

Answer: The fallible conversion rejects negative, non-finite, and finite-but-overflowing inputs without panicking across the cxx boundary. The explicit zero check also rejects tiny positive inputs that round below nanosecond precision, turning every invalid window into an ordinary, catchable C++ exception.

Recap and decision rules

Importing an existing C/C++ header only?  bindgen, then hand-wrap the unsafe surface
Need a two-way, type-checked bridge?       cxx with #[cxx::bridge]
Only Cargo, no separate CMake step?        cxx_build::bridge from build.rs
Evaluating autocxx for new work?           Don't -- follow its README to cxx or Crubit
Considering Crubit today?                  Check crubit.rs status page per feature first
C++ type may be self-referential?          Import it as Pin<&mut T> in the bridge
