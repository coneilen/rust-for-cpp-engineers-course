Lesson 10 · 30 minutes

Locks, Atomics, Deadlocks, and Data Parallelism

Guard shared Pulsewatch state with Mutex and RwLock, understand poisoning, avoid deadlocks by construction, add plain atomic counters where they fit, stay aware of false sharing, and reach for Rayon when the work is an embarrassingly parallel batch.

By the end: You can pick Mutex or RwLock for a piece of shared state, explain what a poisoned lock means and choose a recovery policy, prevent a two-lock deadlock by construction, decide when a plain atomic is enough versus when a lock is required, describe false sharing at a boundary level, and parallelize an independent batch of Pulsewatch probes with Rayon.

Part 1: Mutex and RwLock guards, and what poisoning means

Mutex<T> and RwLock<T> both wrap the data they protect, the same way lesson 8's Cell and RefCell wrapped a value. Calling lock() or read()/write() returns a guard: a value that derefs to the protected data and releases the lock automatically when it is dropped, the same RAII shape as C++'s std::lock_guard, std::unique_lock, or std::shared_mutex.

TypeAccess patternC++ bridge
Mutex<T>One holder at a time, whether reading or writing.std::mutex + std::lock_guard.
RwLock<T>Many concurrent readers, or exactly one writer, never both.std::shared_mutex with shared_lock/unique_lock.

Both return a Result from their locking methods, not the guard directly. If a thread panics while holding the guard, the lock becomes poisoned: every later lock() call returns Err(PoisonError) instead of quietly succeeding. A plain OS mutex has no such concept and hands the lock to the next thread as if nothing happened, even though the panicking thread may have left the protected data half-updated.

Conceptual example — a generic recovery pattern, not tied to one specific file. counters stands for any Mutex-guarded value; Part 6 below applies the same pattern inside PulsewatchStats::record_failure.

let guard = match counters.lock() {
    Ok(guard) => guard,
    Err(poisoned) => {
        // A previous holder panicked while updating this data.
        // Decide deliberately: recover the (possibly inconsistent)
        // data, or propagate as a hard failure.
        poisoned.into_inner()
    }
};

Recovering with into_inner() is reasonable for data whose invariants cannot be broken by a partial update, such as an independent counter. It is the wrong choice for data with cross-field invariants that a panic could have left half-applied; there, propagating the panic (.lock().unwrap()) is safer than silently continuing on corrupted state.

Part 2: deadlocks are not data races, and Rust does not stop them

Data races are prevented by the type system through Send/Sync. Deadlocks are not: two threads can each correctly hold one lock while correctly waiting for the other, and the compiler has no way to see that. Prevention is a discipline, not a guarantee.

Conceptual example — illustrates lock-ordering discipline in the abstract; not part of the pulsewatch-core crate.

Deadlock-prone: order depends on argument order 
fn transfer(from: &Mutex<u64>, to: &Mutex<u64>, amount: u64) {
    let mut from = from.lock().unwrap();
    let mut to = to.lock().unwrap();
    *from -= amount;
    *to += amount;
}
// Thread A: transfer(&x, &y, 10)
// Thread B: transfer(&y, &x, 5)
// A holds x, waits for y. B holds y, waits for x. Neither ever proceeds.
Fixed: always lock in one global order 
fn transfer(a: (&Mutex<u64>, u32), b: (&Mutex<u64>, u32), amount: u64) {
    let ((first, _), (second, _)) = if a.1 < b.1 { (a, b) } else { (b, a) };
    let mut first = first.lock().unwrap();
    let mut second = second.lock().unwrap();
    if a.1 < b.1 {
        *first -= amount;
        *second += amount;
    } else {
        *second -= amount;
        *first += amount;
    }
}
// Every caller locks the lower-id account first, so a circular wait
// between two threads is no longer possible.

A narrower fix that avoids the problem entirely: hold no more than one lock at a time by keeping critical sections short, or merge the two related values into a single Mutex<(u64, u64)> so there is only ever one lock to take. Lesson 9's worker loop follows the "narrow scope" version of this rule: the queue lock is dropped before the probe's own work begins.

Part 3: atomics, and the memory-ordering boundary for this lesson

std::sync::atomic types such as AtomicU64 and AtomicBool let independent, simple values change safely without any lock: no guard, no possibility of poisoning, no possibility of blocking. Every operation takes an Ordering that describes what other memory effects are guaranteed to be visible around it.

OrderingGuaranteeWhen this lesson uses it
RelaxedAtomicity only: the operation cannot tear, but carries no guarantee about the visible order of other memory accesses around it.Independent counters, such as a total-samples tally, where no other value's correctness depends on the counter's exact timing.
SeqCstThe strongest and simplest ordering: a single total order that every thread agrees on for all SeqCst operations.The default to reach for whenever the interaction between an atomic and other shared state is not obviously safe under Relaxed.

The Rustonomicon is explicit that choosing a weaker ordering than SeqCst is only for code that has actually reasoned through the hardware and compiler guarantees involved; this lesson's boundary is to use Relaxed only for counters with no dependency on other data, and SeqCst — or a Mutex — everywhere else. Designing lock-free algorithms with Acquire/Release pairing is out of scope here.

Part 4: false sharing, by name, not yet by measurement

Modern CPUs move memory between cores in fixed-size cache lines, commonly 64 bytes on widely deployed x86_64 hardware. Two unrelated atomics that happen to sit in the same cache line will bounce that line between cores every time either one is updated from a different core, even though the two values have no logical relationship — this is false sharing. It costs real throughput without ever showing up as a correctness bug, so it is easy to miss.

The accepted fix is padding each independently-updated value out to its own cache line. The crossbeam-utils crate's CachePadded<T> wrapper does exactly this. This lesson only asks you to recognize the shape of the problem — profiling for it is deferred to Lesson 18.

Part 5: Rayon for embarrassingly parallel batches

Lesson 9's WorkerPool is the right tool for long-lived, heterogeneous work with explicit lifecycle and backpressure. A different, common shape is a finite batch of independent, similar, CPU-bound items that all need to run once — Pulsewatch sampling every configured probe on a tick, for example. Rayon is a widely used external crate (not part of the standard library) that turns an iterator into parallel work across a managed thread pool with one method call.

rayon = "1"

use rayon::prelude::*;

use crate::{BoxedProbe, Probe, Sample};

pub fn sample_all(probes: &mut [BoxedProbe]) -> Vec<Sample> {
    probes
        .par_iter_mut()
        .map(|probe| probe.sample())
        .collect()
}
ChoiceUse when
Lesson 9's WorkerPoolWork arrives continuously over time, items may differ in kind, and you need explicit shutdown, backpressure, or panic accounting per job.

Part 6: worked Pulsewatch increment — counters that match their invariants

The deciding question is not "lock or atomic," but "does this value have an invariant that spans more than one field?" A lone counter does not; a pair of fields that must describe the same event does.

File: crates/pulsewatch-core/src/stats.rs — create.

use std::sync::atomic::{AtomicU64, Ordering};
use std::sync::{Arc, Mutex};

use crate::Millis;

/// No cross-field invariant: each counter is independently meaningful,
/// so plain atomics are correct and avoid all lock overhead.
#[derive(Default)]
pub struct SampleCounters {
    pub total_samples: AtomicU64,
    pub total_panics: AtomicU64,
}

impl SampleCounters {
    pub fn record_sample(&self) {
        self.total_samples.fetch_add(1, Ordering::Relaxed);
    }

    pub fn record_panic(&self) {
        self.total_panics.fetch_add(1, Ordering::Relaxed);
    }

    pub fn snapshot(&self) -> (u64, u64) {
        (
            self.total_samples.load(Ordering::Relaxed),
            self.total_panics.load(Ordering::Relaxed),
        )
    }
}

/// Cross-field invariant: last_failure_reason always describes
/// last_failure_at. These two fields must change together, so one
/// Mutex-guarded struct is correct -- two separate atomics could be
/// observed in a mismatched, half-updated state.
#[derive(Default)]
struct FailureState {
    last_failure_at: Option<Millis>,
    last_failure_reason: Option<String>,
}

pub struct PulsewatchStats {
    pub counters: SampleCounters,
    failure: Mutex<FailureState>,
}

impl PulsewatchStats {
    pub fn new() -> Arc<Self> {
        Arc::new(Self {
            counters: SampleCounters::default(),
            failure: Mutex::new(FailureState::default()),
        })
    }

    pub fn record_failure(&self, at: Millis, reason: String) {
        self.counters.record_panic();
        let mut guard = self
            .failure
            .lock()
            .unwrap_or_else(|poisoned| poisoned.into_inner());
        guard.last_failure_at = Some(at);
        guard.last_failure_reason = Some(reason);
    } // guard dropped here: lock released before this function returns
}

Wiring this in is a one-line addition per branch, wherever code already handles WorkerEvent values — for example, the loop that drains Lesson 9's outcomes channel after a pool run: call stats.counters.record_sample() for each WorkerEvent::Sampled, and stats.record_failure(now, probe_name) for each WorkerEvent::Panicked. Neither call happens while the job-queue lock from Lesson 9 is held, since that lock is released inside worker_loop before a result is ever sent.

Stability and production boundary

Mutex, RwLock, and std::sync::atomic are all stable standard-library APIs. Rayon is a mature, widely used external crate but is not part of the standard library and must be added as a dependency deliberately. This lesson's atomics usage is deliberately narrow: independent counters with Relaxed, or SeqCst/a lock otherwise. It does not cover designing new lock-free data structures, compare-and-swap retry loops, or `Acquire`/`Release` hand-off protocols — those require the kind of careful, hardware-aware reasoning the Nomicon insists on before dropping below `SeqCst`.

use std::sync::mpsc;

use pulsewatch_core::{
    BoxedProbe, FixedProbe, Millis, Probe, PulsewatchStats, Sample, WorkerEvent, WorkerPool,
    sample_all,
};

struct PanicProbe;

impl Probe for PanicProbe {
    type Output = Sample;

    fn name(&self) -> &str {
        "panic-probe"
    }

    fn sample(&mut self) -> Sample {
        panic!("simulated probe failure")
    }
}

#[test]
fn pool_and_rayon_batches_agree_with_the_shared_counters() {
    let stats = PulsewatchStats::new();

    // 20 probes through the worker pool: 18 succeed, 2 panic.
    let (outcome_tx, outcome_rx) = mpsc::channel();
    let pool = WorkerPool::new(4, outcome_tx);
    for i in 0..18 {
        pool.submit(Box::new(FixedProbe::new(format!("pool-{i}"), Millis::new(1))));
    }
    pool.submit(Box::new(PanicProbe));
    pool.submit(Box::new(PanicProbe));
    pool.shutdown();

    for event in outcome_rx.try_iter() {
        match event {
            WorkerEvent::Sampled(_) => stats.counters.record_sample(),
            WorkerEvent::Panicked { probe_name } => {
                stats.record_failure(Millis::new(0), probe_name)
            }
        }
    }

    // A disjoint batch of 5 probes sampled with Rayon, outside the pool.
    let mut batch: Vec<BoxedProbe> = (0..5)
        .map(|i| {
            Box::new(FixedProbe::new(format!("rayon-{i}"), Millis::new(2))) as BoxedProbe
        })
        .collect();
    let rayon_samples = sample_all(&mut batch);
    for _ in &rayon_samples {
        stats.counters.record_sample();
    }

    let (total_samples, total_panics) = stats.counters.snapshot();
    assert_eq!(total_samples, 18 + 5);
    assert_eq!(total_panics, 2);
    assert_eq!(rayon_samples.len(), 5);
}

Knowledge check

1. Why does a poisoned Mutex return Err from lock() instead of silently handing the lock to the next caller?

Answer: A panic while holding the guard may have left the protected data mid-update. Returning Err(PoisonError) forces the next caller to decide, explicitly, whether it is safe to keep using that data — a plain OS mutex has no equivalent signal.

2. When is RwLock a better fit than Mutex?

Answer: When reads vastly outnumber writes and each read does enough work that letting readers run concurrently is worth the extra bookkeeping an RwLock carries versus a plain Mutex.

3. What specifically causes the deadlock in the transfer example, and what removes it?

Answer: Two threads acquire the same two locks in opposite order, so each ends up waiting for a lock the other already holds — a circular wait. Always acquiring the locks in one fixed, shared order removes the possibility of that cycle.

4. Why does SampleCounters use two separate atomics, while FailureState uses one Mutex-guarded struct?

Answer: The two counters have no invariant linking them, so updating each independently and atomically is correct and cheaper. last_failure_at and last_failure_reason must always describe the same event, so they must change together under one lock; separate atomics could be read in a mismatched, half-updated combination.

Recap and decision rules

Data has no cross-field invariant, single value?    plain atomic (AtomicU64, AtomicBool, ...)
Data has an invariant spanning 2+ fields?            one Mutex<Struct> around all of them together
Reads vastly outnumber writes, reads do real work?   RwLock over Mutex
A previous holder might have panicked mid-update?    match on lock()'s Result; decide recover vs propagate
Two locks needed together?                           acquire in one fixed global order, or merge into one lock
Unsure which memory Ordering is correct?              SeqCst, or a lock -- never guess a weaker one
Several unrelated atomics updated from different threads? consider cache-line padding to avoid false sharing
Finite batch of independent, similar, CPU-bound work?  Rayon par_iter, not a hand-rolled worker pool
Long-lived, heterogeneous work needing lifecycle mgmt? Lesson 9's WorkerPool, not Rayon
