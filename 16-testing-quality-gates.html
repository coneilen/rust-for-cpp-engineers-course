Testing & Quality Gates

Choose deliberately among unit, integration, doc, property, and differential tests for Pulsewatch, filter test runs with cargo test selectors, and gate merges on rustfmt and Clippy.

By the end: you can place a test in the right harness (unit, integration, doc, property, or differential), filter which tests run with cargo test selectors, write a proptest for an invariant, compare new output against recorded legacy C++ output, and wire rustfmt/Clippy into CI as quality gates.

Part 1: five kinds of test, five different jobs

Pulsewatch began as a port of a legacy C++ monitoring tool, and it now has a workspace, a trait-based probe API, an async SQLx-backed server, and formatting rules inherited from the original tool. Each test kind answers a different question:

  • Unit test — a #[cfg(test)] mod tests block beside the code. Compiled into the crate itself, so it can see private items.
  • Integration test — a file under tests/. Each one compiles as its own crate that links only your library's pub surface, the same view an external consumer has.
  • Doc test — a fenced code block inside a doc comment. cargo test compiles and runs it, so a documentation example that stops compiling is a test failure.
  • Property test — a proptest! block that generates many inputs and checks one invariant holds for all of them, shrinking any failing case to a minimal reproduction.
  • Differential test — assert your new implementation's output against recorded output from the system it is replacing, here the legacy C++ formatter.

Part 2: a unit test beside private code

crates/pulsewatch-core/src/probe.rs — append (new private function and its test module)
// pulsewatch-core/src/probe.rs
fn clamp_latency(raw_ms: u64) -> u64 {
    raw_ms.min(60_000)
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn clamp_caps_unreasonable_latency() {
        assert_eq!(clamp_latency(1_000), 1_000);
        assert_eq!(clamp_latency(500_000), 60_000);
    }
}

clamp_latency is a private helper; only a unit test compiled into the same crate can call it directly.

Part 3: an integration test through the public API only

crates/pulsewatch-core/tests/public_api.rs — append (this file already exists from Lesson 7; add this test alongside what is already there)
// pulsewatch-core/tests/public_api.rs
use pulsewatch_core::{FixedProbe, Millis, Probe};

#[test]
fn fixed_probe_reports_configured_latency() {
    let mut probe = FixedProbe::new("db-primary", Millis::new(42));
    let sample = probe.sample();
    assert_eq!(sample.latency.get(), 42);
}

This file cannot reach clamp_latency even if it tried: tests/public_api.rs is compiled as a separate crate that only sees what pulsewatch-core re-exports. That is exactly the boundary an external caller sees, which is why integration tests catch "it compiles inside the crate but the public API can't actually do this" mistakes that unit tests miss.

Part 4: a doc test that is also documentation

crates/pulsewatch-core/src/probe.rs — replace the existing struct Millis(u64); line with this doc-commented version
/// Wraps a millisecond latency so it cannot be confused with a plain count.
///
/// ```
/// use pulsewatch_core::Millis;
///
/// let latency = Millis::new(120);
/// assert_eq!(latency.get(), 120);
/// ```
pub struct Millis(u64);

The fenced block compiles and runs under cargo test --doc. A code example here that no longer matches the real API fails the build instead of quietly going stale in a comment.

Part 5: a property test for an invariant

proptest is a dev-dependency, added once to the library package that owns the tests directory:

crates/pulsewatch-core/Cargo.toml — append to the existing [dev-dependencies] table (create the table if it is not present yet)
proptest = "1"
crates/pulsewatch-core/tests/property.rs — create
// pulsewatch-core/tests/property.rs
use proptest::prelude::*;
use pulsewatch_core::Millis;

proptest! {
    #[test]
    fn millis_roundtrips_any_value(raw in any::<u64>()) {
        let latency = Millis::new(raw);
        prop_assert_eq!(latency.get(), raw);
    }
}

proptest generates hundreds of values for raw, including edge cases like 0 and u64::MAX, and shrinks any failure to the smallest input that still fails. A handful of hand-picked example tests would not have chosen those edge cases for you.

Part 6: a differential test against the legacy C++ output

crates/pulsewatch-core/tests/differential.rs — create
// pulsewatch-core/tests/differential.rs
use pulsewatch_core::{Millis, Sample};

// Captured once from the legacy C++ CLI: `pw_legacy --format <source> <ms>`.
const LEGACY_FIXTURES: &[(&str, u64, &str)] = &[
    ("db-primary", 4, "db-primary: 004ms"),
    ("db-primary", 128, "db-primary: 128ms"),
    ("edge-us-east", 12, "edge-us-east: 012ms"),
    ("edge-us-east", 9001, "edge-us-east: 9001ms"),
];

/// Mirrors the legacy CLI's own text formatter, so both sides of the
/// comparison below are exercising the same field values, not two
/// independently-invented string layouts.
fn format_sample(sample: &Sample) -> String {
    format!("{}: {:03}ms", sample.source, sample.latency.get())
}

#[test]
fn matches_legacy_cpp_formatting() {
    for &(source, ms, expected) in LEGACY_FIXTURES {
        let sample = Sample { source: source.to_string(), latency: Millis::new(ms) };
        assert_eq!(format_sample(&sample), expected, "mismatch for {source} at {ms}ms");
    }
}

The fixture values were recorded once from the legacy tool's own output, including its %03u-style zero padding below 1000ms. format_sample reads Sample's own source field and calls Millis::get rather than any nonexistent method on Sample itself; Rust's {:03} width-and-zero-pad specifier matches C's %03u without truncating values that are already wider than three digits. A differential test like this proves the new formatter is byte-for-byte compatible on the recorded inputs; it says nothing about inputs nobody captured.

Part 7: selecting which tests run, and gating on style

Run every command below from the workspace root:

cargo test --lib                 # unit tests only
cargo test --test public_api     # one integration-test binary
cargo test --doc                 # doc tests only
cargo test clamp                 # name-substring filter across all harnesses
cargo test -- --ignored          # tests marked #[ignore]
cargo test -- --nocapture        # show println! output even on pass

cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace
cargo test --workspace --doc

cargo fmt --check fails instead of reformatting when style drifts; -D warnings promotes every Clippy lint to a hard error so a merge cannot silently accumulate warnings.

Read the Rust: syntax mapped to C++

RustMeaningC++ bridge
#[cfg(test)] mod testsCompiles this module only for test builds, in the same crate as the code it tests.Closest to a friend test fixture compiled only into the test binary, but built into the language.
tests/*.rsEach file is its own crate, linking only the library's public API.Like a separate test executable that only includes your public headers, not internal ones.
/// ``` ... ```A documentation example that is compiled and executed as a test.Similar to a Doxygen \code block, except it is not just illustrative — it must actually run.
proptest! { ... }Generates many inputs and checks one property holds, shrinking failures.A QuickCheck-style generator, comparable to RapidCheck in C++.
cargo test <substring>Filters tests across all harnesses by name substring.Similar to ctest -R style test filtering, but by plain substring instead of a regular expression.
cargo clippy -- -D warningsRuns the linter and treats every warning as a build failure.Comparable to enabling -Werror over a wide extra lint set, like clang-tidy checks promoted to errors.

Worked Pulsewatch increment

The five test kinds above now cover Pulsewatch end to end: a unit test for the private clamping rule, an integration test that only exercises what pulsewatch-core exports, a doc test that keeps Millis's example honest, a property test for the newtype's round-trip invariant, and a differential test proving the new formatter matches the legacy C++ tool's recorded output. cargo fmt --check and cargo clippy -D warnings gate style and lint issues before any of this even runs.

🧭
Stability and production boundary

Passing tests are evidence, not a guarantee: the differential test only covers the four fixture values that were actually captured from the legacy tool, the property test only covers the properties you wrote assertions for, and none of this replaces a real code review. Treat a green CI run as "no known regression," not "correct for all inputs."

Active exercise

  1. In crates/pulsewatch-core/tests/differential.rs (append), add one more entry to LEGACY_FIXTURES for a latency at or above 100000ms, for example ("edge-us-east", 100_000, "edge-us-east: 100000ms").
  2. From the workspace root, run cargo test -p pulsewatch-core --test differential. Expected evidence: matches_legacy_cpp_formatting still passes with the fifth fixture; if it fails, the failure message names the exact fixture your padding assumption got wrong.
  3. In crates/pulsewatch-core/src/probe.rs (replace the #[derive(...)] line above pub struct Millis(u64);), add PartialOrd, Ord to the derive list if either is missing, so it reads #[derive(Debug, Clone, Copy, PartialEq, Eq, PartialOrd, Ord)].
  4. In crates/pulsewatch-core/tests/property.rs (append), add a second property: 
    proptest! {
    #[test]
    fn millis_preserves_ordering(a in any::<u64>(), b in any::<u64>()) {
        prop_assume!(a < b);
        prop_assert!(Millis::new(a) < Millis::new(b));
    }
}
  5. From the workspace root, run cargo test -p pulsewatch-core --test property. Expected evidence: both millis_roundtrips_any_value and millis_preserves_ordering pass, each reporting 256 generated cases by default.
  6. From the workspace root, run these four commands separately and note which test names appear in each one's output: cargo test -p pulsewatch-core --lib, cargo test -p pulsewatch-core --test public_api, cargo test -p pulsewatch-core --doc, cargo test --workspace. Expected evidence: --lib lists only clamp_caps_unreasonable_latency; --test public_api lists only fixed_probe_reports_configured_latency; --doc lists only the Millis example; --workspace lists all of the above plus property and differential.
  7. From the workspace root, run cargo fmt --all -- --check. Expected evidence: exits with no output and status 0; if it reports a diff, run cargo fmt --all (without --check) to apply it, then re-run the check.
  8. From the workspace root, run cargo clippy --workspace --all-targets --all-features -- -D warnings. Expected evidence: exits with status 0 and no warnings; fix any reported lint at the file and line Clippy names, then re-run the command.

Knowledge check

1. Why can tests/public_api.rs not call clamp_latency even though it lives in the same workspace?

Answer: Each file under tests/ compiles as its own crate that only sees the library's pub surface, the same view an external consumer has; private items are simply not visible from there.

2. What does the property test in Part 5 check that the unit test in Part 2 does not?

Answer: It checks the round-trip invariant across hundreds of generated u64 values, including edge cases like 0 and u64::MAX, rather than only the handful of values a person chose to write down.

3. Why run cargo clippy --workspace --all-targets --all-features -- -D warnings in CI instead of just cargo build?

Answer: It runs the linter across every target and feature combination and turns every warning into a build failure, catching issues a plain build would only ever print as a warning that could be ignored.

4. What does a passing differential test against the legacy fixtures prove, and what does it not prove?

Answer: It proves the new formatter's output is byte-identical to the legacy C++ tool's recorded output for exactly the captured inputs; it says nothing about inputs nobody recorded a fixture for.

Recap and decision rules

Testing one private function/module invariant?  Unit test beside the code
Testing only the public crate surface?           Integration test under tests/
Documenting and verifying an example at once?    Doc test
Checking a property across many generated inputs? proptest
Comparing against a known-good legacy system?    Differential test with recorded fixtures
Style/lint gate before merge?                    cargo fmt --check + cargo clippy -D warnings in CI
