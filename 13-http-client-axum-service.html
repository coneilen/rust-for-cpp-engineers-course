Lesson 13 · 30 minutes

HTTP Client and Service with reqwest and axum

Add an HTTP-based probe kind to Pulsewatch with a reusable reqwest::Client, then expose Pulsewatch itself as a small axum service with a JSON check endpoint, middleware, graceful shutdown, and an in-process test.

By the end: You can configure a shared reqwest::Client with timeouts and a response-size limit, build an axum router with extractors and shared state, serialize responses with serde, layer tower middleware, shut a service down gracefully, and test a handler without binding a real socket.

Part 1: an HTTP probe needs one reused client, not one per call

Lessons 11 and 12 gave Pulsewatch a raw TCP probe. Many real targets instead expose an HTTP health endpoint such as GET /healthz. reqwest builds on the Tokio runtime from Lesson 12 and gives Pulsewatch a real HTTP client instead of hand-rolling HTTP framing on top of Lesson 11's sockets.

This lesson's HTTP and service code builds toward one new file, crates/pulsewatch-cli/src/http_probe.rs, another sibling module of Lesson 11's tcp_probe.rs and Lesson 12's async_probe.rs in the same pulsewatch-cli package. Parts 1 through 3 below are excerpts that explain one function at a time; the exercise in Part 4 gives that file's complete, exact contents to create.

Excerpt from crates/pulsewatch-cli/src/http_probe.rs (illustrates the reusable client and the bounded chunk-streaming read; the exercise gives the complete file):

use std::time::Duration;

pub fn build_http_client() -> reqwest::Result<reqwest::Client> {
    reqwest::Client::builder()
        .connect_timeout(Duration::from_secs(3))
        .timeout(Duration::from_secs(5))
        .pool_max_idle_per_host(8)
        .build()
}

pub async fn probe_http(
    client: &reqwest::Client,
    url: &str,
) -> Result<pulsewatch_core::ProbeOutcome, reqwest::Error> {
    const MAX_BODY_BYTES: usize = 64 * 1024;
    let started = tokio::time::Instant::now();

    let mut response = client.get(url).send().await?;
    let status = response.status();

    // Content-Length is only a declared hint, and reqwest's own docs note it
    // can be absent or stale once a gzipped body is auto-decoded. Rejecting
    // early on an already-oversized declared length is a cheap optimization,
    // but it must not be the only guard: a missing, wrong, or chunked-encoded
    // length would let it through unchecked.
    if let Some(len) = response.content_length() {
        if len as usize > MAX_BODY_BYTES {
            return Ok(pulsewatch_core::ProbeOutcome {
                target: url.to_string(),
                success: false,
                latency_ms: started.elapsed().as_millis(),
                message: format!("body too large: {len} declared bytes"),
            });
        }
    }

    // The real cap: stream the body one chunk at a time and add each
    // chunk's length to a running total before buffering it, so an unknown,
    // chunked-transfer, or decompressed-larger-than-declared body is bounded
    // by what is actually received, not by what the server claimed.
    let mut body = Vec::new();
    while let Some(chunk) = response.chunk().await? {
        if body.len() + chunk.len() > MAX_BODY_BYTES {
            return Ok(pulsewatch_core::ProbeOutcome {
                target: url.to_string(),
                success: false,
                latency_ms: started.elapsed().as_millis(),
                message: format!("body exceeded {MAX_BODY_BYTES} bytes while streaming"),
            });
        }
        body.extend_from_slice(&chunk);
    }

    let text = String::from_utf8_lossy(&body);
    Ok(pulsewatch_core::ProbeOutcome {
        target: url.to_string(),
        success: status.is_success(),
        latency_ms: started.elapsed().as_millis(),
        message: format!("{status}: {text}"),
    })
}
Rust syntaxMeaningC++ bridge
reqwest::Client::builder()...build()Configures and constructs one client, expected to be created once and reused (it internally pools connections and DNS caches).Comparable to constructing one long-lived curl multi-handle or HTTP session object instead of a fresh handle per request.
.connect_timeout(...) / .timeout(...)Separately bounds the connection-establishment phase and the whole request/response round trip.Roughly CURLOPT_CONNECTTIMEOUT versus CURLOPT_TIMEOUT.
response.content_length()Reads the response's known body length, if any — an early-rejection optimization only; it can be absent, or wrong once a compressed body is auto-decoded, so it is never the only guard.Similar to checking a header value before a read, while knowing that header can lie or be missing — never a substitute for bounding the read itself.
response.chunk().awaitPulls one piece of the response body at a time inside a while let Some(chunk) = ... loop, returning None once the body is exhausted; the caller controls how much it accumulates.Comparable to repeated bounded recv() calls on a socket, checking the running total after each one, instead of one unbounded read-to-end.
⚠️
TLS, redirects, and SSRF are the caller's responsibility

reqwest defaults to following redirects and validating TLS certificates against the system trust store, both sensible defaults for a monitoring client. But if Pulsewatch's target URLs ever come from user input, an attacker-controlled URL that resolves to an internal address is a server-side request forgery (SSRF) risk: the check runs from inside your network with your service's credentials. Production Pulsewatch would validate and restrict target hosts before ever calling client.get(url), and would consider capping or disabling redirect following with ClientBuilder::redirect for targets it does not fully trust.

Part 2: axum turns Pulsewatch itself into a small HTTP service

Alongside probing others, Pulsewatch now exposes its own status over HTTP: an operator or another service can ask it what it has observed. axum builds routers out of composable handler functions.

Excerpt from crates/pulsewatch-cli/src/http_probe.rs (the router and its handlers; the exercise gives the complete file):

use axum::{extract::State, routing::get, Json, Router};
use std::sync::Arc;

#[derive(Clone)]
struct AppState {
    http_client: reqwest::Client,
}

async fn health() -> &'static str {
    "ok"
}

async fn check_target(
    State(state): State<Arc<AppState>>,
    axum::extract::Path(url): axum::extract::Path<String>,
) -> Json<pulsewatch_core::ProbeOutcomeDto> {
    let outcome = probe_http(&state.http_client, &url)
        .await
        .unwrap_or_else(|err| pulsewatch_core::ProbeOutcome {
            target: url.clone(),
            success: false,
            latency_ms: 0,
            message: err.to_string(),
        });
    Json(outcome.into())
}

pub fn build_router(state: Arc<AppState>) -> Router {
    Router::new()
        .route("/healthz", get(health))
        .route("/check/{*url}", get(check_target))
        .with_state(state)
}
Rust syntaxMeaningC++ bridge
Router::new().route(path, get(handler))Registers handler for GET requests on path; each handler is an ordinary async function, matched by its parameter types.Closer to a declarative route table (as in many C++ REST frameworks built on Boost.Beast) than to manually parsing a request line and dispatching by hand.
State(state): State<Arc<AppState>>An extractor: axum inspects the handler's parameter types and supplies each one by pulling it out of the request or the shared application state.No direct analogue; closest to dependency injection resolved by parameter type at each call, rather than through a constructor.
axum::extract::Path(url): Path<String>Extracts the matched wildcard segment of the URL path directly into a typed value.Comparable to a route framework binding a URL template capture group to a typed handler parameter.
Json<pulsewatch_core::ProbeOutcomeDto>Both an extractor (for request bodies) and a response type; here it serializes the returned value as the JSON response body.Similar to a framework's typed response wrapper that sets Content-Type: application/json and serializes automatically.
.with_state(state)Attaches shared, cloneable application state so every handler can extract it via State<T>.Comparable to storing a shared service-locator object that request handlers can access, but type-checked per handler.
🧩
Why the DTO instead of returning ProbeOutcome directly?

Pulsewatch's internal ProbeOutcome may gain fields over time that are not meant for external API consumers. A small, explicit ProbeOutcomeDto that implements serde::Serialize keeps the wire format stable and reviewed even as the internal type evolves — a discipline familiar from any service that separates its persistence or domain model from its public API contract.

Part 3: JSON with serde, middleware with tower, and graceful shutdown

ProbeOutcomeDto is a wire-format type, not internal probe logic, so — like ProbeOutcome in Lesson 11 — it belongs in pulsewatch-core, not in the service module that calls it. check_target above already references it fully qualified as pulsewatch_core::ProbeOutcomeDto, which is only valid Rust if the type truly lives outside the crate that contains check_target.

Append to crates/pulsewatch-core/src/outcome.rs (this file already contains ProbeOutcome from Lesson 11; add the following below it, in the same file, in the same module — so the From impl below refers to ProbeOutcome with no crate-name prefix, since it is already in scope in this file):

// crates/pulsewatch-core/src/outcome.rs (append)
use serde::Serialize;

#[derive(Serialize)]
pub struct ProbeOutcomeDto {
    pub target: String,
    pub success: bool,
    pub latency_ms: u128,
    pub message: String,
}

impl From<ProbeOutcome> for ProbeOutcomeDto {
    fn from(outcome: ProbeOutcome) -> Self {
        Self {
            target: outcome.target,
            success: outcome.success,
            latency_ms: outcome.latency_ms,
            message: outcome.message,
        }
    }
}

Append to crates/pulsewatch-core/src/lib.rs (add one more re-export next to the existing pub use outcome::ProbeOutcome; line from Lesson 11):

// crates/pulsewatch-core/src/lib.rs (append)
pub use outcome::ProbeOutcomeDto;

Append to crates/pulsewatch-core/Cargo.toml under its [dependencies] table (this is the first lesson to add an external dependency to pulsewatch-core itself, since #[derive(Serialize)] is used directly in this crate's own source):

# crates/pulsewatch-core/Cargo.toml (append under [dependencies])
serde = { version = "1", features = ["derive"] }

#[derive(Serialize)] generates the code that walks each field and writes it out through whichever format serde is asked to target; axum::Json, in the service module, asks for the JSON one. No field is written or parsed by hand.

Excerpt from crates/pulsewatch-cli/src/http_probe.rs (middleware layering and graceful shutdown; the exercise gives the complete file):

use tower_http::limit::RequestBodyLimitLayer;
use tower_http::timeout::TimeoutLayer;
use std::time::Duration;

pub fn build_router_with_middleware(state: Arc<AppState>) -> Router {
    build_router(state)
        .layer(RequestBodyLimitLayer::new(64 * 1024))
        .layer(TimeoutLayer::new(Duration::from_secs(10)))
}

pub async fn serve(router: Router, addr: std::net::SocketAddr) -> std::io::Result<()> {
    let listener = tokio::net::TcpListener::bind(addr).await?;
    axum::serve(listener, router)
        .with_graceful_shutdown(shutdown_signal())
        .await
}

async fn shutdown_signal() {
    tokio::signal::ctrl_c()
        .await
        .expect("failed to install Ctrl+C handler");
}
Rust syntaxMeaningC++ bridge
.layer(SomeLayer)Wraps the whole router in a tower::Service middleware; layers apply to every route registered before the call.Comparable to registering a middleware/filter chain in front of a request dispatcher.
RequestBodyLimitLayer::new(64 * 1024)Rejects any request whose body (by declared or actual length) exceeds the given byte cap before a handler ever sees it.Similar to configuring a maximum request size at a reverse proxy or web server layer rather than trusting each handler to check it.
axum::serve(listener, router).with_graceful_shutdown(fut)Serves connections until fut completes, then stops accepting new connections while letting in-flight ones finish.Analogous to a signal handler that closes the listening socket and waits for outstanding requests to drain instead of terminating mid-response.

    client: &reqwest::Client,
    url: &str,
) -> Result<pulsewatch_core::ProbeOutcome, reqwest::Error> {

Knowledge check

1. Why build one reqwest::Client and share it, instead of constructing a new client per probe?

Answer: A Client owns pooled connections and cached DNS lookups; reusing it lets subsequent requests to the same host skip a fresh TCP and TLS handshake. Constructing a new client per call throws that pooling away and adds latency and resource churn to every probe.

2. What determines which parts of an incoming request an axum handler parameter receives?

Answer: Each parameter's type is an extractor axum knows how to construct from the request or the router's shared state — for example, State<T> pulls shared application state, and Path<String> pulls a matched URL segment. The handler's signature declares what it needs; axum wires it up.

3. Why does this lesson stream the body in a chunk() loop instead of trusting content_length() alone before calling response.text().await?

Answer: Content-Length is only a declared hint: it can be missing, wrong, or bypassed entirely by chunked transfer encoding or a compressed body that expands on decode. Checking it first is a cheap optimization for the common case, but only adding each chunk's length to a running total and erroring once it crosses the cap — before the bytes are appended to the buffer — actually bounds memory use regardless of what the server declared or how the body was framed.

4. What does with_graceful_shutdown actually change about how the service stops?

Answer: Without it, stopping the process (or dropping the listener) can cut off in-flight requests mid-response. With it, the server stops accepting new connections once the shutdown future completes but continues serving requests already in progress until they finish.

Recap and decision rules

Calling out to other services over HTTP?         Build one reqwest::Client, reuse it
Bound the request/connect time?                    ClientBuilder::timeout / connect_timeout
Body size cannot be trusted?                        Stream chunk() and check a running total, not just content_length
Target host comes from user input?                  Validate/restrict it; watch for SSRF
Exposing your own HTTP API?                          axum::Router with typed extractors
Need shared config/clients in handlers?              .with_state(Arc<AppState>)
Cross-cutting request handling (limits, timeouts)?   tower_http layers via .layer(...)
Testing a handler without a real socket?             tower::ServiceExt::oneshot
Stopping without dropping in-flight requests?        axum::serve(...).with_graceful_shutdown(...)
