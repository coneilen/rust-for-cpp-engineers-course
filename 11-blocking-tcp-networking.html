Lesson 11 · 30 minutes

Blocking TCP Networking with std::net

Give Pulsewatch its first real probe: a hand-rolled, newline-framed TCP protocol built on std::net, tested end to end on loopback, with explicit timeouts and an honest boundary around what blocking sockets should never be asked to do.

By the end: You can open and accept TCP connections with std::net, reason about who owns a TcpStream, split it into a buffered reader and writer, define a tiny line-based framing rule, set read/write timeouts, and explain why this lesson stops before TLS or a real HTTP implementation.

Part 1: a listener and a stream are two different ownership stories

Pulsewatch is a small monitoring tool: it holds a list of targets and periodically checks whether each one answers. Every check so far has been conceptual. This lesson gives Pulsewatch its first real network call, built entirely on the standard library, no async runtime yet. Parts 1 through 3 below walk through three pieces of one eventual file, crates/pulsewatch-cli/src/tcp_probe.rs, one concept at a time; each piece shown here is an excerpt to explain the idea, not yet the file's final content — the exercise in Part 4 gives that file's complete, exact contents to create.

std::net::TcpListener owns a bound, listening socket. Calling .incoming() yields one io::Result<TcpStream> per accepted connection. Each TcpStream is an independent, owned handle to one connected socket — there is no shared listener state once accept succeeds.

Excerpt from crates/pulsewatch-cli/src/tcp_probe.rs (illustrates TcpListener; the exercise gives the complete file):

use std::net::TcpListener;

fn run_server(bind_addr: &str) -> std::io::Result<()> {
    let listener = TcpListener::bind(bind_addr)?;
    println!("pulsewatch-probe listening on {}", listener.local_addr()?);

    for incoming in listener.incoming() {
        let stream = incoming?;
        std::thread::spawn(move || {
            if let Err(err) = handle_connection(stream) {
                eprintln!("connection error: {err}");
            }
        });
    }
    Ok(())
}
Rust syntaxMeaningC++ bridge
TcpListener::bind(addr)Resolves addr, then performs socket, bind, and listen in one call, returning io::Result<TcpListener>.Roughly getaddrinfo + socket(2) + bind(2) + listen(2), with errors returned instead of checked via errno.
listener.incoming()An iterator of io::Result<TcpStream>; each item is one accepted connection.A loop around accept(2) that already wraps the resulting file descriptor in an owning type.
TcpStreamAn owned, moveable handle to one connected socket; dropping it closes the socket.Comparable to a raw socket file descriptor wrapped in RAII, similar in spirit to boost::asio::ip::tcp::socket.
move || { ... }Moves the accepted stream into a new OS thread; no other owner can touch it afterward.Unlike passing a raw fd into std::thread and hoping nobody double-closes it, the compiler enforces single ownership.
⚠️
Thread-per-connection does not scale forever

One OS thread per connection is fine for a loopback probe tool and small fan-out. It stops being fine somewhere in the low thousands of concurrent connections because of per-thread stack memory and context-switch overhead. Lesson 12 keeps this exact protocol but moves the scheduler onto Tokio so Pulsewatch can probe far more targets concurrently without one thread per target.

Part 2: splitting one stream into a reader and a writer

Read and Write both require &mut self. If Pulsewatch's protocol needs to read a reply while a write is logically still "in flight," one TcpStream value cannot be borrowed mutably from two places at once. The standard fix is try_clone, which duplicates the underlying socket handle so reads and writes proceed independently against the same OS socket.

Excerpt from crates/pulsewatch-cli/src/tcp_probe.rs (an early, unbounded draft of handle_connection; Part 4 replaces this with a bounded version — do not create this draft as its own file):

use std::io::{BufRead, BufReader, Write};
use std::net::TcpStream;

fn handle_connection(stream: TcpStream) -> std::io::Result<()> {
    stream.set_read_timeout(Some(std::time::Duration::from_secs(5)))?;

    let mut writer = stream.try_clone()?;
    let mut reader = BufReader::new(stream);

    let mut line = String::new();
    reader.read_line(&mut line)?;
    let request = line.trim_end();

    match request.strip_prefix("PING ") {
        Some(token) if !token.is_empty() => writeln!(writer, "PONG {token}")?,
        _ => writeln!(writer, "ERR bad-request")?,
    }
    Ok(())
}
Rust syntaxMeaningC++ bridge
stream.try_clone()Duplicates the socket handle; both values refer to the same underlying connection and can be moved to different owners (here, a BufReader and a plain writer).Closest to dup(2) on a socket file descriptor: two independent handles, one underlying resource.
BufReader::new(stream)Wraps the stream so repeated small reads pull from an in-process buffer instead of issuing a syscall every time.Comparable to wrapping a raw descriptor in a buffered std::istream-like adapter.
reader.read_line(&mut line)Reads bytes, appending to line, until it sees \n or the connection ends; loops internally over partial reads.Similar to std::getline, but it operates over a socket instead of an in-memory or file stream, and returns a byte count plus an io::Result.
request.strip_prefix("PING ")Returns Some(rest) only when the line starts with the literal prefix; otherwise None.Roughly rfind at position 0 plus a substring, but returning an Option instead of an index that must be checked against npos.
🧩
Framing is a rule you invent, not a rule the socket enforces

TCP delivers an ordered byte stream with no message boundaries at all. read_line only works because both sides agree, out of band, that \n ends a message. A malicious or buggy peer that never sends \n would make read_line keep growing line forever without a size cap — one reason production framing code bounds the buffer explicitly, which the exercise below adds.

Part 3: the client side, timeouts, and DNS resolution

The client half of the probe protocol connects, writes a request line, and reads exactly one reply line, timing the round trip. Its result needs a stable, shared shape, because Lessons 12 through 14 all return, wrap, and store this same value — so it belongs in pulsewatch-core, the reusable library crate Lesson 7 set up at crates/pulsewatch-core/, not as a type defined privately inside whichever binary happens to call probe_once.

Create crates/pulsewatch-core/src/outcome.rs with exactly this content:

// crates/pulsewatch-core/src/outcome.rs
#[derive(Debug)]
pub struct ProbeOutcome {
    pub target: String,
    pub success: bool,
    pub latency_ms: u128,
    pub message: String,
}

Append to crates/pulsewatch-core/src/lib.rs (add these four lines after Lesson 7's existing mod probe; / pub use probe::{...}; lines; do not remove those existing lines):

// crates/pulsewatch-core/src/lib.rs (append)
mod outcome;

pub use outcome::ProbeOutcome;

ProbeOutcome lives in its own module, outcome.rs, alongside Lesson 7's probe.rs, and lib.rs re-exports it the same way it already re-exports Probe, Sample, FixedProbe, and Millis. Every caller outside the crate reaches it as pulsewatch_core::ProbeOutcome — one definition, one export path. Lessons 12, 13, and 14 all depend on pulsewatch-core and import this exact type; none of them declares its own ProbeOutcome.

The probe protocol logic itself (probe_once, and handle_connection from Part 2) lives in the other workspace crate, pulsewatch-cli, at crates/pulsewatch-cli/src/tcp_probe.rs — not inside pulsewatch-core. Rust only lets code write a crate's own name as a path prefix (pulsewatch_core::ProbeOutcome) from outside that crate; code living inside pulsewatch-core itself would have to write crate::ProbeOutcome instead. Keeping tcp_probe.rs in pulsewatch-cli, which already depends on pulsewatch-core as declared in Lesson 7, is what makes the fully-qualified pulsewatch_core::ProbeOutcome spelling below both valid and the spelling every later lesson reuses.

Excerpt from crates/pulsewatch-cli/src/tcp_probe.rs (the client half; the exercise gives the complete file, combining this with the bounded server half from Part 4):

use std::io::{BufRead, BufReader, Write};
use std::net::TcpStream;
use std::time::{Duration, Instant};

pub fn probe_once(
    host: &str,
    port: u16,
    timeout: Duration,
) -> std::io::Result<pulsewatch_core::ProbeOutcome> {
    let target = format!("{host}:{port}");
    let started = Instant::now();

    let stream = TcpStream::connect(&target)?;
    stream.set_read_timeout(Some(timeout))?;
    stream.set_write_timeout(Some(timeout))?;

    let mut writer = stream.try_clone()?;
    let mut reader = BufReader::new(stream);

    writeln!(writer, "PING pulsewatch-v1")?;
    writer.flush()?;

    let mut line = String::new();
    reader.read_line(&mut line)?;
    let latency_ms = started.elapsed().as_millis();
    let reply = line.trim_end();

    Ok(pulsewatch_core::ProbeOutcome {
        target,
        success: reply.starts_with("PONG"),
        latency_ms,
        message: reply.to_string(),
    })
}
QuestionAnswer in this code
Why does probe_once return pulsewatch_core::ProbeOutcome instead of a type it declares itself?The blocking client here, the Tokio wrapper in Lesson 12, the HTTP probe in Lesson 13, and the SQLite persistence layer in Lesson 14 all need to agree on one result shape. Defining it once in pulsewatch-core and importing it everywhere else means the compiler rejects any lesson that drifts out of sync, instead of four incompatible structs that happen to share a name.
Where does DNS resolution happen?TcpStream::connect(&target) accepts anything implementing ToSocketAddrs. A "host:port" string is resolved to one or more SocketAddr values, and connect tries them in order until one succeeds or all fail.
What happens if the peer never replies?set_read_timeout bounds how long read_line will block; past that, it returns io::ErrorKind::WouldBlock/TimedOut, which ? propagates as an Err instead of hanging the calling thread forever.
What happens if the connect step itself hangs?connect has no built-in timeout on all platforms; production code typically uses TcpStream::connect_timeout with an explicit SocketAddr when the peer might be unreachable rather than merely slow to reply.
Why measure latency with Instant rather than SystemTime?Instant is monotonic and immune to wall-clock adjustments; SystemTime can jump backward, which would corrupt an elapsed-duration calculation.

Excerpt only (a side-by-side illustration of the framing problem described above — neither snippet is a file to create or edit):

Fragile: assume one read gets the whole reply
let mut buf = [0u8; 64];
let n = reader.read(&mut buf)?;
let reply = std::str::from_utf8(&buf[..n])
    .unwrap();
Robust: read until the agreed frame boundary
let mut line = String::new();
reader.read_line(&mut line)?;
let reply = line.trim_end();

A single TcpStream::read call may return anywhere from one byte to the full reply, split arbitrarily across TCP segments. The left column silently assumes the whole message arrived in one read; read_line on the right loops internally until the frame boundary appears, which is the behavior a byte-stream protocol actually needs.

Part 4: exercise — a bounded, tested Pulsewatch probe on loopback

This exercise creates four new files that, together, are the complete, runnable form of everything Parts 1 through 3 introduced piece by piece. Work through the numbered steps in order from the workspace root.

  1. Create crates/pulsewatch-cli/src/lib.rs (this file does not exist yet; Lesson 7 gave pulsewatch-cli only a src/main.rs). No Cargo.toml edit is needed — Cargo automatically treats src/lib.rs as the package's library target and src/main.rs/src/bin/*.rs as its binaries once the file exists. 
    // crates/pulsewatch-cli/src/lib.rs
pub mod tcp_probe;
  2. Create crates/pulsewatch-cli/src/tcp_probe.rs with exactly this content — it supersedes the Part 1/Part 2/Part 3 excerpts above by combining the bind loop, a bounded handle_connection capped at MAX_LINE_BYTES, probe_once, and a loopback test in one file: 
    // crates/pulsewatch-cli/src/tcp_probe.rs
use std::io::{BufRead, BufReader, Read, Write};
use std::net::{TcpListener, TcpStream};
use std::time::{Duration, Instant};

const MAX_LINE_BYTES: usize = 256;

pub fn run_server(bind_addr: &str) -> std::io::Result<()> {
    let listener = TcpListener::bind(bind_addr)?;
    println!("pulsewatch-probe listening on {}", listener.local_addr()?);

    for incoming in listener.incoming() {
        let stream = incoming?;
        std::thread::spawn(move || {
            if let Err(err) = handle_connection(stream) {
                eprintln!("connection error: {err}");
            }
        });
    }
    Ok(())
}

pub fn handle_connection(stream: TcpStream) -> std::io::Result<()> {
    stream.set_read_timeout(Some(Duration::from_secs(5)))?;
    let mut writer = stream.try_clone()?;
    let mut reader = BufReader::new(stream).take(MAX_LINE_BYTES as u64);

    let mut line = String::new();
    reader.read_line(&mut line)?;

    if !line.ends_with('\n') {
        writeln!(writer, "ERR line-too-long")?;
        return Ok(());
    }

    match line.trim_end().strip_prefix("PING ") {
        Some(token) if !token.is_empty() => writeln!(writer, "PONG {token}")?,
        _ => writeln!(writer, "ERR bad-request")?,
    }
    Ok(())
}

pub fn probe_once(
    host: &str,
    port: u16,
    timeout: Duration,
) -> std::io::Result<pulsewatch_core::ProbeOutcome> {
    let target = format!("{host}:{port}");
    let started = Instant::now();

    let stream = TcpStream::connect(&target)?;
    stream.set_read_timeout(Some(timeout))?;
    stream.set_write_timeout(Some(timeout))?;

    let mut writer = stream.try_clone()?;
    let mut reader = BufReader::new(stream);

    writeln!(writer, "PING pulsewatch-v1")?;
    writer.flush()?;

    let mut line = String::new();
    reader.read_line(&mut line)?;
    let latency_ms = started.elapsed().as_millis();
    let reply = line.trim_end();

    Ok(pulsewatch_core::ProbeOutcome {
        target,
        success: reply.starts_with("PONG"),
        latency_ms,
        message: reply.to_string(),
    })
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn loopback_ping_pong_round_trip() {
        let listener = TcpListener::bind("127.0.0.1:0").expect("bind loopback");
        let addr = listener.local_addr().expect("local addr");

        std::thread::spawn(move || {
            for incoming in listener.incoming() {
                let stream = incoming.expect("accept");
                handle_connection(stream).expect("handle connection");
            }
        });

        let outcome = probe_once(
            &addr.ip().to_string(),
            addr.port(),
            Duration::from_secs(2),
        )
        .expect("probe_once should succeed");

        assert!(outcome.success);
        assert!(outcome.message.starts_with("PONG"));
    }
}

    BufReader::take(MAX_LINE_BYTES as u64) wraps the reader in an adapter that reports end-of-input once that many bytes have been read, so an unterminated line stops growing memory instead of consuming it without bound. Binding to 127.0.0.1:0 asks the OS to assign an unused port, keeping the test independent of any port already in use; local_addr() reports back which port was actually chosen.

🚧
Explicitly out of scope for this lesson

This protocol is intentionally not TLS and not HTTP. Hand-rolling encryption is a well-known way to introduce serious, hard-to-notice vulnerabilities; production Pulsewatch would terminate TLS with an audited crate such as rustls rather than add encryption to this line protocol by hand. Likewise, reimplementing HTTP framing, headers, and status codes from raw sockets duplicates work that reqwest and axum already do correctly — that work starts in Lesson 13.

Knowledge check

1. Why does handle_connection call stream.try_clone() instead of reading and writing through one shared TcpStream value?

Answer: Read and Write both take &mut self, so one value cannot be mutably borrowed for reading and writing at the same time in the same scope. try_clone duplicates the socket handle so a reader and a writer can be owned and used independently while referring to the same underlying connection.

2. Why can a single call to TcpStream::read not be trusted to return one complete Pulsewatch message?

Answer: TCP is a byte stream with no built-in message boundaries; a read call may return part of a message, one message, or several, split arbitrarily by the network stack. read_line loops internally until the agreed-upon \n boundary appears, which handles partial reads correctly where a single fixed-size read would not.

3. What does TcpStream::connect("host:port") do before it opens a socket?

Answer: The string argument implements ToSocketAddrs, so connect first resolves the host through DNS (or parses it directly if it is already an IP literal) into one or more SocketAddr values, then tries each in turn until a connection succeeds or all attempts fail.

4. Why does this lesson cap the request line at MAX_LINE_BYTES instead of trusting read_line alone?

Answer: read_line keeps appending bytes until it finds \n or the connection closes; a peer that never sends a newline would make the buffer grow without bound. Wrapping the reader in .take(MAX_LINE_BYTES as u64) forces end-of-input once that many bytes are read, turning an unbounded hang or memory grow into a bounded, reportable error.

5. Where is ProbeOutcome actually defined, and why does probe_once return pulsewatch_core::ProbeOutcome instead of declaring its own struct?

Answer: ProbeOutcome is defined once, in crates/pulsewatch-core/src/outcome.rs, and re-exported from that crate's lib.rs as pulsewatch_core::ProbeOutcome. probe_once imports and returns that exact type rather than a locally declared one so that Lesson 12's async wrapper, Lesson 13's HTTP probe and DTO conversion, and Lesson 14's SQLite persistence all operate on one shared, compiler-checked type — not four separately declared structs that merely share a name and would not type-check against each other.

Recap and decision rules

Need a quick blocking prototype on loopback?   std::net::{TcpListener, TcpStream}
Need independent read and write access?         stream.try_clone(), one handle each
Reading small amounts repeatedly?               Wrap in BufReader / BufWriter
Message boundaries matter?                      Pick and document a framing rule (here: newline)
Peer might stall or vanish?                     set_read_timeout / set_write_timeout
Untrusted or unbounded input?                    Cap the buffer (.take(N)) before parsing
Need encryption?                                 Reach for rustls; do not hand-roll TLS
A result type is shared across lessons/crates?   Define it once in pulsewatch-core, import everywhere
Need thousands of concurrent connections?        Move to async (Lesson 12)
