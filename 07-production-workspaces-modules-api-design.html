Lesson 7 · 30 minutes

Production Workspaces, Modules, and API Design

Start Pulsewatch, a production monitoring system, as a Cargo workspace: a reusable core library, a thin CLI adapter, and a small, deliberate public API behind unit and integration tests.

By the end: You can create a multi-package Cargo workspace, explain package/crate/module boundaries, expose a stable public API with visibility rules and re-exports, use a newtype and an associated type deliberately, and back the API with unit and integration tests.
📁

Part 1: from one binary to a product-shaped workspace

Lessons 1–6 built rust-greeter as one package with one binary crate. Pulsewatch starts differently: a reusable library that other tools can depend on, plus a CLI that only wires it up. Four terms matter, and they are not interchangeable:

Rust termWhat it isC++ bridge
PackageOne Cargo.toml manifest describing a name, version, and dependencies.Closest to one project/solution file, not one source file.
CrateOne compilation unit: a library crate or a binary crate. A package may contain one library crate and several binary crates.Closest to one linked translation-unit graph that produces one artifact.
ModuleA namespace and privacy boundary inside a crate, declared with mod. Modules do not have to map one-to-one to files.Closer to a C++ namespace than to a header, and it also controls visibility.
WorkspaceSeveral packages sharing one Cargo.lock and one target/ build output directory.Closest to a multi-project solution with one shared dependency lock.

Pulsewatch will grow across the rest of this course, so it starts as a workspace with two packages: a library that later lessons extend, and a CLI that stays a thin adapter.

Run from: the empty parent folder you chose in the setup box above.

mkdir pulsewatch
cd pulsewatch
cargo new --lib crates/pulsewatch-core
cargo new --bin crates/pulsewatch-cli

Each cargo new call writes one manifest and one starter source file: crates/pulsewatch-core/Cargo.toml plus a placeholder crates/pulsewatch-core/src/lib.rs, and crates/pulsewatch-cli/Cargo.toml plus a placeholder crates/pulsewatch-cli/src/main.rs that prints "Hello, world!". Both placeholders are replaced later in this lesson — the listings below show their final contents.

After the four commands above, lib.rs and main.rs still hold Cargo's defaults and probe.rs does not exist yet. This is the target layout once every file in Part 3 is in place:

pulsewatch/
├── Cargo.toml                    # [workspace] — no package of its own
├── crates/
│   ├── pulsewatch-core/          # reusable library package
│   │   ├── Cargo.toml
│   │   └── src/
│   │       ├── lib.rs
│   │       └── probe.rs
│   └── pulsewatch-cli/           # executable package
│       ├── Cargo.toml
│       └── src/
│           └── main.rs

File: pulsewatch/Cargo.toml — create. cargo new only writes each package's own manifest, so you add this workspace-root manifest by hand.

[workspace]
members = ["crates/pulsewatch-core", "crates/pulsewatch-cli"]
resolver = "3"
🧭
Why resolver = "3" is written explicitly

"3" is the dependency-resolver version that a normal package gets automatically from edition = "2024". This root Cargo.toml is a virtual workspace: it lists members but owns no package of its own, so it has no edition to infer a resolver from. The version is set directly in the [workspace] table instead.

Part 2: design the API from the consumer inward

In Rust, everything defaults to private to its module. A struct field, function, or module is visible outside its module only if marked pub, and how far pub reaches can be narrowed further.

Visibility syntaxReachesC++ bridge
fn helper() { ... }Private to the current module and its children (the Rust default).Similar intent to a function in an anonymous namespace or a private class member, but the boundary is the module, not the class.
pub(crate) fn helper()Visible anywhere in this crate, never to a dependent crate.No exact match; closer to an internal-linkage symbol shared across one binary's translation units.
pub fn helper()Visible to any crate that can reach the containing module.Similar intent to a symbol declared in a public header.
pub use probe::{Probe, Sample};Re-exports names at a shorter, chosen path without moving the code that defines them.Closest to a curated umbrella header, but re-exports are checked paths, not textual inclusion.

Re-exports matter because internal module names should stay free to change. Callers write pulsewatch_core::Probe; whether that type is actually defined in probe.rs, probe/mod.rs, or a future split file is an internal detail the re-export hides.

A newtype stops units from mixing silently

A bare u64 milliseconds value and a bare u64 sample count look identical to the compiler. A newtype, a tuple struct with one field, gives them different types:

Conceptual excerpt — do not create a separate file for this. The same code becomes part of crates/pulsewatch-core/src/probe.rs in Part 3.

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub struct Millis(u64);

impl Millis {
    pub fn new(value: u64) -> Self {
        Self(value)
    }

    pub fn get(self) -> u64 {
        self.0
    }
}

Because the inner field stays private, no caller outside this module can construct a Millis from an arbitrary integer or read its value without going through new and get. That is close to a strong C++ typedef built from a class with an explicit constructor, except the Rust compiler always enforces it — a raw u64 can never implicitly convert into a Millis.

An associated type lets each implementation pick one output

Conceptual excerpt — the complete trait, with its Sample output type, is defined in crates/pulsewatch-core/src/probe.rs in Part 3.

pub trait Probe {
    type Output;
    fn name(&self) -> &str;
    fn sample(&mut self) -> Self::Output;
}

type Output; declares an associated type: every implementation of Probe chooses one concrete Output, and callers write P::Output instead of supplying it themselves. This differs from a generic trait parameter such as trait Probe<T>, where one type could implement the trait multiple times for different T. Pulsewatch wants exactly one output shape per probe type, so an associated type states that intent directly.

Part 3: the first probe behind a small public API

File: crates/pulsewatch-core/src/lib.rs — replace the placeholder cargo new wrote.

// crates/pulsewatch-core/src/lib.rs
mod probe;

pub use probe::{FixedProbe, Millis, Probe, Sample};

File: crates/pulsewatch-core/src/probe.rs — create (this file does not exist after cargo new).

// crates/pulsewatch-core/src/probe.rs
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub struct Millis(u64);

impl Millis {
    pub fn new(value: u64) -> Self {
        Self(value)
    }

    pub fn get(self) -> u64 {
        self.0
    }
}

pub trait Probe {
    type Output;
    fn name(&self) -> &str;
    fn sample(&mut self) -> Self::Output;
}

#[derive(Debug, PartialEq, Eq)]
pub struct Sample {
    pub source: String,
    pub latency: Millis,
}

pub struct FixedProbe {
    name: String,
    latency: Millis,
}

impl FixedProbe {
    pub fn new(name: impl Into<String>, latency: Millis) -> Self {
        Self { name: name.into(), latency }
    }
}

impl Probe for FixedProbe {
    type Output = Sample;

    fn name(&self) -> &str {
        &self.name
    }

    fn sample(&mut self) -> Sample {
        Sample { source: self.name.clone(), latency: self.latency }
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn fixed_probe_reports_configured_latency() {
        let mut probe = FixedProbe::new("cpu", Millis::new(12));
        let sample = probe.sample();
        assert_eq!(sample.source, "cpu");
        assert_eq!(sample.latency.get(), 12);
    }
}
New lineWhy it exists
impl Into<String>Accepts either an owned String or a &str literal and converts once inside the constructor, instead of forcing every caller to allocate first.
Self { name: name.into(), latency }Self means “the type this impl block is for,” here FixedProbe. The shorthand field latency means latency: latency.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]Generates standard value operations: formatted printing, bitwise duplication for Copy types, and structural equality. Deriving is a request to the compiler, not hand-written boilerplate.
#[cfg(test)] mod testsCompiles this module only for test builds. use super::*; reaches into the parent module, so unit tests may use private fields that the public API hides.
 
// crates/pulsewatch-cli/src/main.rs
use pulsewatch_core::{FixedProbe, Millis, Probe};

fn main() {
    let mut probe = FixedProbe::new("startup", Millis::new(5));
    let sample = probe.sample();
    println!("{} reported {} ms", sample.source, sample.latency.get());
}

The CLI never touches probe.rs directly. It only sees the re-exported names pulsewatch_core::{FixedProbe, Millis, Probe}, exactly the vocabulary Part 2 chose to expose.

Run from: pulsewatch/ (the workspace root).

cargo run -p pulsewatch-cli

Expected output: startup reported 5 ms.

Part 4: tests are part of the public API surface

The unit test inside probe.rs can reach private fields because it lives in a child module. An integration test lives in a separate tests/ directory, compiles as its own crate, and can only see what the library actually exports:

File: crates/pulsewatch-core/tests/public_api.rs — create (the tests/ directory does not exist yet either).

// crates/pulsewatch-core/tests/public_api.rs
use pulsewatch_core::{FixedProbe, Millis, Probe};

#[test]
fn constructs_probe_through_public_api_only() {
    let mut probe = FixedProbe::new("network", Millis::new(42));
    let first = probe.sample();
    let second = probe.sample();

    assert_eq!(first.latency.get(), 42);
    assert_eq!(second.latency.get(), 42);
}

If this test could reach probe::Millis(42) directly, or construct Sample with a field the design meant to keep read-only from outside, the re-export boundary would be incomplete. An integration test failing to compile against private internals is itself useful evidence that the boundary holds.

Run from: pulsewatch/ (the workspace root).

cargo test --workspace

Expected output: two passing test binaries — pulsewatch-core's unit tests report test result: ok. 1 passed (fixed_probe_reports_configured_latency), and the public_api integration test reports test result: ok. 1 passed (constructs_probe_through_public_api_only).

🧭
Stability and production boundary

Modules, visibility rules, re-exports, associated types, newtypes, workspaces, and resolver = "3" are all stable Rust and Cargo features. A pub struct field is a compatibility promise to every dependent crate; prefer a private field with a constructor and accessor when the invariant may change later, exactly as Millis does here. As the workspace grows, keep shared dependency versions in one root [workspace.dependencies] table instead of repeating them per package.

Knowledge check

1. What is the compilation unit: package, crate, or module?

Answer: A crate. A package describes one or more crates through its manifest; a module organizes names and privacy inside one crate.

2. Why re-export names instead of making every module public?

Answer: A re-export creates a small, chosen, stable path for consumers while the internal module layout and file structure stay free to change without breaking dependents.

3. Why does Millis keep its inner u64 private?

Answer: A private field forces every value to pass through Millis::new, preventing a plain integer meant for a different unit from being used as milliseconds by mistake.

4. When should a trait use an associated type instead of a generic parameter?

Answer: When each implementing type should settle on exactly one related output type and callers should not choose or repeat that type themselves, as Probe::Output does for every probe.

Recap and decision rules

Shared lockfile and build output across packages? Workspace
One compiled library or binary?                    Crate
Namespace and privacy boundary inside a crate?      Module
Public path should stay small and stable?           Re-export the chosen names
Two values share a primitive type but not a unit?   Newtype
Every implementation needs exactly one output type? Associated type
Testing private internals?                          Unit test inside the module
Testing only the exported surface?                  Integration test under tests/
